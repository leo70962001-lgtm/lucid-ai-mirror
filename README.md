# LUCID AI Smart Mirror — 可執行 Demo

四步驟流程的可操作網頁原型：拍照推薦・合成美妝 → 推薦美妝產品 → AR 上妝體驗 → 給正面評價（見〈流程調整為四步〉）。不是簡報動畫，是真的會跑臉部偵測、真的算膚色、真的即時上妝。

## 在別台電腦上打開

先講一個**繞不過去的限制**：相機（`getUserMedia`）只在 **`https://` 或 `localhost`** 底下能用。用 `file://` 直接開檔案，任何瀏覽器都會擋掉相機 —— 這是瀏覽器的安全規則，不是設定問題。

所以有三條路，取捨不同：

| | 怎麼給 | 對方要裝什麼 | 相機 |
|---|---|---|---|
| **A. 單檔** | 傳 `lucid-demo.html`（18 MB，專案根目錄）| 什麼都不用，雙擊開啟 | ✗ 只能上傳照片 |
| **B. 本機啟動** | 傳整包，對方點 `start.bat` / `start.sh` | Node 或 Python（多數開發機都有）| ✓ |
| **C. 靜態託管** | `dist/site/` 整包丟上 HTTPS 空間 | 什麼都不用，開網址 | ✓ |

**要展示完整流程就選 C。** 拖到 Netlify Drop、Cloudflare Pages 或 GitHub Pages 都可以，不需要後端、不需要 CLI，`dist/site/` 是純靜態的。

單檔版（A）能跑**上傳照片之後的完整流程**：膚色分析與妝容合成 → 推薦產品 → 靜態上妝預覽 → 評價與體驗報告。少的只有即時相機。

### 三個版本都不依賴網路

MediaPipe 的 WASM（9.4 MB）與臉部模型（3.7 MB）原本走 CDN。**櫃位機台常常沒有外網，連不到就整個卡在開機畫面**，所以全部改成本機資源：

```bash
node vendor.mjs     # 抓外部依賴到 vendor/（一次就好，22 MB）
node build.mjs      # 產出 dist/
```

`index.html` 現在**零外部連線**。單檔版把 WASM、模型、12 張商品照、QR 函式庫全部 base64 內嵌，開機時轉成 blob URL —— 開啟後不會發出任何對外請求。代價是檔案 18 MB。

要小檔案可以用 `node build.mjs --online`（約 0.8 MB，但需要網路）。**預設是離線版**，因為一個小但打不開的檔案沒有價值。

### 建置時會擋下的三件事

1. **頂層命名衝突** —— 六個模組併成單一 scope 後撞名，JS 只會丟難查的 `Identifier has already been declared`。建置時掃描，撞名直接中止。目前 126 個宣告、零衝突。
2. **離線資源缺檔** —— 少 vendor 檔案就中止並告訴你要跑 `node vendor.mjs`，不會產出一個半殘的檔案。
3. **靜態主機沒有伺服器端點** —— `images/products/index.json` 會產成實體檔案。

### 踩過的四個坑

1. **`file://` 下模組腳本不執行** —— opaque origin 會踩到 CORS，整段 JS 不跑，**畫面只是靜靜卡在開機畫面什麼都不說**。單檔版改用傳統 `<script>`（併成單一 scope 後本來就不需要模組語意），並加了全域錯誤攔截把失敗顯示在開機畫面上。
2. **全域變數在模組頂層取值太早** —— 單檔版的 blob URL 要等 base64 轉換完成，`face.js` 在頂層取值會抓到預設路徑。改成呼叫時才讀。
3. **`import()` 與 `fetch()` 的相對路徑基準不同** —— 動態 `import('./vendor/…')` 相對於**模組自己的 URL**（`/js/face.js` → `/js/vendor/…` 404），`fetch()` 相對於**文件**。兩個都改成 `new URL(p, document.baseURI)`。這個坑會讓每一個託管版本都掛掉。
4. **`.mjs` 的 MIME 各家主機不一致** —— 模組匯入會拒絕非 JavaScript 的 MIME，有些主機把 `.mjs` 回成 `application/octet-stream`。vendor 的 bundle 存成 `.js`，不賭對方主機的設定。

### 本機開發

```bash
node server.js      # http://localhost:5173
node test.mjs       # 12 組邏輯驗證，不需瀏覽器
```

## 七個關鍵技術決策

### 1. 478 個關鍵點，不是企劃書寫的 68 點

68 點的唇部只有 12 個點，畫不出內外唇線，唇彩會糊出唇緣。478 點才有足夠的唇部與眼周精度。

### 2. product-first，不是 style-first

企劃書 Step 2 寫的是「AI 妝容風格遷移引擎」生成妝容，Step 3 再「解構」出商品。這條路在實務上會產生「AI 畫了一個很美的妝，但找不到對應商品」。

本 demo 反過來做：`LOOKS` 只描述角色配置與強度，**不含任何顏色**；顏色一律來自 `PRODUCTS` 的實測色值。所以 Step 4 渲染出來的顏色，保證等於 Step 3 推薦的那支商品的色值 —— 所見即所得，不需要反推。

`test.mjs` 第 5 組驗證了這點：36 個推薦全部命中真實且有庫存的商品。

### 3. 用 canvas `'color'` 混合模式上色

```js
ctx.globalCompositeOperation = 'color';   // 色相+彩度取自來源，明度取自底圖
ctx.fillStyle = product.color;
ctx.fill(lipPath);
```

這一行就是 illumination-aware 的關鍵：臉上原本的陰影、反光、皮膚紋理全部保留，只有顏色被替換。這是 Yang et al. (Eurographics 2023) 把 bare skin / makeup / illumination 分離那個想法的輕量版。

差別在論文能做 relighting，這裡不能 —— 但「顏色不會被當下環境光烘死」這個最關鍵的性質是一樣的。

**為什麼沒用 three.js**：論文的 UV-space 方法要跑 3DMM inverse rendering + GAN inpainting，非即時，且相依的 Basel Face Model 是學術非商業授權。Demo 階段用 2D canvas 是對的選擇；真要走 3D 路線是產品化階段的事，屆時才需要 three.js 把 UV 材質貼到 face mesh 上。

### 4. 用眼白做環境光補償

櫃位的燈光幾乎不會是 D65。暖光下每個人的膚色取樣都會偏黃，底調殘差整批位移 —— **前面校準得再準，一放到真實櫃位就失效**。

臉上有一個現成的中性參考物：**眼白**。關鍵點本來就有，取樣時濾掉睫毛、虹膜與眼窩陰影（亮度 < 60 或彩度 > 22% 就丟掉），再取最亮的四成避開上眼瞼投影。

灰世界假設在這裡不能用 —— 畫面被臉佔滿，把平均拉成灰等於直接抹掉我們要測的膚色資訊。

三個做對了才會準的細節：

1. **在線性空間做** —— 光源在物理上是乘在線性光量上，不是乘在 sRGB 的 gamma 編碼值上。直接對 0–255 做乘除會有系統性誤差。
2. **亮度也要還原** —— 光源同時改變顏色**和**亮度，而底調基準線 `h ≈ 0.249·L* + 47` 是吃 L\* 的。只還原色度不還原亮度，基準線就會拿到錯的 L\*。單張影像無法從曝光反推絕對亮度，所以拿眼白當**曝光錨點**（名目反射率 Y=0.72，約 L\* 88）。
3. **可信度只看色度** —— 2700K 鹵素燈的藍色增益本來就會到 4 倍以上，那是正常櫃位燈光，不該被當異常擋掉。要擋的是有色光、墨鏡、眼睛半閉。

`test.mjs` 第 9 組用**普朗克軌跡**（Kim et al. 2002）算出真實色溫的光源做驗證，不是隨手編的比例：

| | 結果 |
|---|---|
| 不補償 | **5/12** 組被燈光帶偏（2700K 鹵素燈把暖膚色判成中性、8000K 冷白把中性判成冷調）|
| 補償後 | **12/12** 還原成 D65 下的判定 |

畫面上會顯示估到的色溫與眼白取樣點數；估不到就明說「未補償」並提示判定可能偏移，不會假裝有把握。

### 5. Step 4 的 AR：先量再改

<http://localhost:5173/_ar.html>

沒有相機也能驗證渲染器：合成一張**張嘴露牙**的臉（口腔填白色當牙齒，兩頰做左右明暗漸層當側光），再量效能。

**修掉的正確性問題：唇彩會塗到牙齒上。**

原本只用外唇輪廓 `LIPS_OUTER`。閉嘴時看不出來，但只要張嘴笑，口腔就整片被塗成唇色。改成外輪廓 + 內輪廓 `LIPS_INNER` 兩個環，用 `fill(path, 'evenodd')` 把口腔挖掉。閉嘴時內輪廓面積趨近 0，所以外觀不變。

測試台五項全過：牙齒 **ΔE 0.00**（完全沒被動到）、唇帶上色 ΔE 47.2、唇色色相差 2.1°、明暗比例 1.084 → 1.085、區域外 ΔE 0.00。

**效能：我一開始改錯地方。**

先把渲染從「整張畫布」改成「只處理區域邊界框」，以為會是大勝。實測打臉：

| 解析度 | 整張畫布 | 只處理邊界框 | 加速 |
|---|---|---|---|
| 640×480 | 1.21 ms | 0.87 ms | 1.4× |
| 1280×960 | 1.14 ms | 1.02 ms | 1.1× |
| 1920×1440 | 1.43 ms | 1.27 ms | 1.1× |

第一次量還更離譜：全畫布「比較快」。原因是 **canvas 指令是非同步送去 GPU 的**，`performance.now()` 量到的是送出指令的時間而不是執行時間。在計時區段末讀一個像素強制 flush 才對。

真正的瓶頸在別的地方：

| 每幀組成 | | |
|---|---|---|
| 臉部追蹤（MediaPipe） | 18.6 ms | **96%** |
| 上妝渲染 | 0.9 ms | 4% |

所以正確的解法是**把追蹤頻率和渲染頻率拆開** —— 臉不會每毫秒都在動。追蹤跑 30Hz，畫面每個 vsync 都重畫：

| | 吞吐量 |
|---|---|
| 每幀都追蹤 | 49 fps |
| 追蹤 30Hz + 每幀渲染 | 589 fps（**12.1×**）|

（這是不受 vsync 限制的吞吐量；實際顯示仍鎖在 60fps，但多出來的餘裕正是弱一點的機台需要的。）

邊界框那段只有 1.1–1.4×，遠不如我預期，但仍保留 —— 它讓離屏緩衝區的大小跟著臉走而不是跟著畫布走，1920×1440 下可省下約 11 MB/緩衝區，這對整合顯示晶片的機台有意義。

### 6. 遮擋、嘴角、漸層唇

三項都在 `_ar.html` 用 A/B 驗證 —— 同一支渲染器、只改一個開關，才能確定差異真的來自那個機制。**測試台目前 12 項全過。**

**遮擋拒斥**

頭髮、眼鏡框擋在臉前時，MediaPipe 仍會「猜」出關鍵點，妝就直接畫在遮擋物上。完整解法要跑分割模型，但追蹤已經吃掉 96% 的幀預算，再加一個模型不划算。

改用**暗色遮擋物拒斥**：比周圍明顯暗的像素不上妝。用 SVG 的 `feColorMatrix type="luminanceToAlpha"` 把亮度轉成 alpha，再用 `destination-in` 讓 alpha 相乘 —— 全程在 GPU 上跑，**不需要把像素讀回 CPU**（讀回會造成管線停頓）。

亮度門檻以 Step 2 量到的膚色明度為基準，所以深膚色不會被自己的膚色觸發拒斥；用固定門檻就會。

| 深色髮絲穿過下唇 | 遮擋開 | 遮擋關 |
|---|---|---|
| 髮上 | **ΔE 0.0** | ΔE 28.4（被塗到）|
| 旁邊的唇 | ΔE 42.1 | — |

**擋得住**：頭髮、眼鏡框、睫毛、鼻孔、強陰影。
**擋不住**：手掌等膚色接近的遮擋物 —— 那需要分割模型。

**嘴角收斂**

原本整圈同一個羽化寬度，嘴角會看起來腫一塊。改成在兩側嘴角（關鍵點 61 / 291）疊 `destination-out` 的徑向漸層。嘴角/中央濃度比 **1.02 → 0.53**，中央濃度不變（ΔE 46.5 → 46.5）。

**漸層唇**

韓系內濃外淡。用**橢圓形**的 alpha 衰減 —— 圓形漸層在嘴角會退得太快。由 `LOOKS` 的 `lipGradient` 開啟（目前只有韓系微光妝）。

第一版垂直半徑設成 `lipH × 0.62`，結果下唇帶中央就掉了 25%（ΔE 46.5 → 34.8）—— 那是「整片變淡」不是「往外緣淡」。改成 `× 0.95` 後：外側 ΔE 47.6 → **24.2**（變淡），內側 46.5 → **45.1**（維持）。

**代價**：渲染從 0.9 ms 增加到 2.26 ms（多兩道 filter 與遮罩），仍只佔 30fps 預算的 7%。追蹤依舊是 85% 的瓶頸。

### 6b. 真人實測：上妝根本看不出來

前面所有驗證都用合成關鍵點，**從沒測過真人臉**。實機一跑就發現唇彩幾乎沒效果。拿真人臉重現後量出兩個原因：

**① 遮擋閘門的門檻壓在嘴唇身上**

閘門原本設 `膚色亮度 × 0.25 ~ 0.50`。但**嘴唇天生就比皮膚暗** —— 實測真人唇帶平均亮度是膚色的 **0.46 倍**，正好落在閘門斜坡上，整片唇被當成半個遮擋物，**砍掉三分之一**（ΔE 12.6 → 8.4）。

改成 `× 0.16 ~ 0.30`。這個區間是量出來的：唇帶 0.46 倍、深色頭髮 0.12 倍，門檻要落在兩者之間。我一度改成 `0.10 ~ 0.22`，唇是救回來了但**遮擋失效**（測試台的「頭髮上未被上色」從 ΔE 0.0 變成 14.8）—— 兩邊都要顧。

**② `'color'` 混合本身在真人臉上太含蓄**

`'color'` 完全保留底圖明度、只換色相彩度。但真人嘴唇本來就偏紅、明度範圍又寬，換個色相的視覺差異很小 —— 數值上「正確」，體感上「沒上到妝」。

加了 **coverage（覆蓋率）**：在 `'color'` 之後再往商品色本身收斂一段，等於把明度範圍壓向商品的明度、彩度拉向商品的彩度，同時保留 (1−coverage) 的原始明暗。真實唇膏本來就是半不透明的，這一步才決定「有沒有上到妝」。唇 0.72、眼影 0.46、腮紅 0.42。

霧面的 multiply 也從 0.28 降到 0.15 —— 它會把剛鋪上的商品色又壓暗回去，等於把 coverage 做的事抵銷掉。

**修好之後在真人臉上的實測**

| 色號 | 唇帶平均 ΔE |
|---|---|
| #118 玫瑰豆沙 | 13.3 |
| #204 蜜楓棕 | 18.2 |
| #620 莓果紫紅 | 22.7 |
| #307 冷調正紅 | **30.9** |

**色號本身的差異比任何參數都大。** 玫瑰豆沙 `rgb(192,107,107)` 跟真實唇色 `rgb(127,76,62)` 只差 ΔE 22，所以它天生就是最含蓄的那一支；冷調正紅差 2.3 倍。第一次實測剛好推薦到玫瑰豆沙、又開著分屏（只有半邊上妝）、又碰上沒修的閘門 —— 三件事疊在一起才會「完全看不出來」。

**另外兩個順手修的**

- **追蹤掉幀時妝會一閃一閃地掉**。原本偵測失敗就立刻清掉關鍵點。改成沿用上一組最多 300 ms。
- **`detectForVideo` 的時間戳必須嚴格遞增**，一旦回退整個 CalculatorGraph 會直接失敗且不會自己復原。主程式用 rAF 時間戳所以沒踩到，但我寫效能模擬時踩爆了。已在 `face.js` 強制單調遞增，變成呼叫端不需要煩惱的事。
- Step 4 畫面右上角新增即時讀數（fps + 追蹤耗時 + 是否偵測到臉），掉幀時看得見。

### 7. 顯示端校色

<http://localhost:5173/_calib.html>

Step 4 算出來的顏色是**數值上正確**的，但螢幕會用自己的原色與 gamma 去呈現它。機台螢幕不是 sRGB 標準的話，顧客看到的唇色就不等於實品 —— 這是前面所有色彩工作的最後一哩。

**這一步需要色差儀，沒有捷徑。** 這個模組不負責量測，負責的是「拿到量測值之後」的擬合、校正與驗證。

用標準的顯示器特性化模型：

```
量測值(XYZ) = M · (code^γ)
校正        = 目標 XYZ → M⁻¹ → 裝置線性 → γ 編碼 → 送給螢幕的碼值
```

量測 13 個色塊（三通道各四階 + 白）。頁面有全螢幕色塊模式，色差儀才有足夠面積量。沒有硬體的話按「示範：模擬一台偏掉的螢幕」可以跑完整條流程看效果。

`test.mjs` 第 11 組模擬一台「三原色偏移 + 每通道 gamma 不一致」的便宜面板：

| 情境 | 校正前 | 校正後 |
|---|---|---|
| 理想量測 | ΔE 6.1 | **0.27** |
| ±0.5% 色差儀雜訊 | 6.1 | **0.43** |
| 面板非純冪次響應 | 6.3 | **1.31**（4.8× 改善）|

**三個踩過的坑**

1. **量化** —— `0.25 × 255` 會被 round 成 64，實際階調是 `64/255 = 0.25098`。用名目值 0.25 擬合會讓 gamma 系統性偏低（2.447 vs 真值 2.450）。
2. **參考螢幕的轉換函數** —— 我一開始把 sRGB 螢幕模擬成純 `x^2.2`，但 sRGB 的轉換是**分段的**（有線性趾部）。兩者差約 1 ΔE，而我把這個誤差算進了校正結果。
3. **單位尺度** —— 色差儀的輸出單位不固定（有的給 cd/m²，有的以白 = 100），而校正目標的 XYZ 是 0–1 尺度。第一版沒正規化，網頁上的校正後 ΔE 直接變成 **66.6**（比不校正還糟）。而且它**不會報錯，只會安靜地產生完全錯誤的顏色** —— 這是真實部署最容易中招的地方。現在以「模型白」的 Y 正規化，並有一組測試專門驗證「量測值放大 100 倍，結果必須不變」。

**接進主程式**：`_calib.html` 按「套用到 demo」後，Step 3 的色票、商品圖與 Step 4 的 AR 都會走校正後的色值。畫面底部會顯示 **「螢幕已校色 γ …」** 或 **「螢幕未校色」** —— 未校色時要看得見，不能讓人以為顏色是準的。

**還沒做的**：商品照片（`images/products/`）不會被校正，那需要離線重新處理整批圖檔。色票與 AR 已涵蓋，那是顧客判斷顏色的主要依據。

## 已知限制（誠實說明）

- **膚色分類的公平性**：底調用「相對於同明度基準線的色相殘差」判定，基準線 `h ≈ 0.249·L* + 47.0` 由 6 個涵蓋 Fitzpatrick I–VI 的樣本回歸而得。深膚色會主動顯示信心不足的提示，而不是假裝有把握。正式上線前需要用真實分層資料重新校準。
- **螢幕校色**：擬合、校正與驗證都已實作（見上面「顯示端校色」），但**量測需要色差儀**。沒有量測值時主程式會明確顯示「螢幕未校色」。商品照片尚未納入校正。
- **效能**：AR 畫布固定 640px 寬。實測瓶頸是臉部追蹤（96%）不是渲染，已用追蹤降頻處理；若要更快得換更小的模型或改 WebGL。
- **無後端**：評分與購物車只寫到 console，沒有真的送出。

### 為什麼要校色

生圖時只給了商品 id、沒給色值，所以模型自己編了顏色。結果是 **12 張全部對不上**，ΔE 9.7–42.1：

| 問題 | 實測 |
|---|---|
| 系統性偏暗 | 唇彩 L* 宣告 41–64 → 照片 27–54，每一支都變暗 |
| 最嚴重 | L512 蜜桃汽水（淺暖桃 L*64）→ 照片是深酒紅 L*31，ΔE 35.5 |
| E02 / E03 對調 | 目錄 E02 玫瑰灰粉(h 10°) → 照片金色(h 71°)；E03 香檳裸金(h 76°) → 照片灰色(h 36°) |

直接採用照片顏色不可行 —— 唇彩會全部塌成暗色系，暖膚色使用者就沒有合適的推薦了。

所以改成**用色值回頭校正照片**：在 Lab 空間只搬色相與彩度，明度按彩度加權微調。照片原本的高光、陰影、質感全部保留，黑色管身（彩度≈0）幾乎不動。跟 `makeup.js` 用 `'color'` 混合模式是同一個想法：換顏色，不換光。

E03 需要特別處理：來源是灰色（彩度≈5），**沒有色相可以旋轉、彩度也乘不起來**。低彩度來源改用明度開窗（L\* 22–82）區分盤面與黑框白蓋，直接把目標色相塗上去。ΔE 從 32.5 降到 0.8。

校正後全部 12 張 ΔE 落在 **0.2–1.0**，Step 3 的商品照與 Step 4 的 AR 渲染保證同色。

>
> 但這些是 AI 生成的模型圖，**不是實拍**。正式上線要換成實品攝影，並用色差儀量測 D65 標準光源下的 Lab 值作為 `color` 的權威來源。

## 啟動器為什麼是純英文

`start.bat` 刻意只用 ASCII。在批次檔裡放 UTF-8 中文會弄壞 cmd.exe 的解析 —— `chcp 65001` 之後 cmd 會用新編碼重新讀取剩下的位元組，多位元組字元被切碎，**連 `REM` 註解行都會開始被當成指令執行**。實測時整個腳本亂掉：`pause` 提前觸發、`cd /d` 找不到磁碟機、框線字元被當成指令名。

中文說明因此獨立成 `HOW-TO-RUN.txt`（純文字檔沒有這個問題）。`start.sh` 不受影響，維持中文。

`server.js` 的啟動訊息也改成純 ASCII —— 原本的 `→` 在 Windows 主控台會顯示成亂碼。

## 上妝渲染器 v2：UV 貼圖 + WebGL 網格變形

第一版是在 2D canvas 上直接沿臉部輪廓畫路徑再模糊。實機測試後換掉了，因為它有兩個**結構性**的問題 —— 不是參數調不好，是數學上做不到。

做法參考 `D:\ai\mirrorme-demo`（演算法照抄，API 改成配合本專案的商品目錄）。

### 一、只有乘性，畫不出珠光

舊版用 canvas 的 `'color'` 混合，本質是乘法。**乘法只能讓皮膚變暗** —— 珠光、打亮、遮瑕在數學上就畫不出來。

新版用 Yang et al.(EG 2023) 的三通道合成式，在著色器裡一行算完：

```glsl
made = skin * m.rgb + b.rgb * b.a / max(m.a, 0.004);
```

`blend` 是乘性色偏（顏料吸光），`bias` 是加性補光（珠光反光）。商品的**質地**直接對應 `bias`：霧面 0、水光 24、珠光 40。

### 二、平塗加模糊一定看起來假

真實妝感的差別幾乎都在**漸層的方向**，不在顏色。新版每個部位有自己的漸層軸：

| 部位 | 漸層軸 |
|---|---|
| 眼影 | 睫毛根部 → 眉骨（暈染高度可調）|
| 腮紅 | 中心 → 外圍（放射，位置可在蘋果肌與顴骨間移動）|
| 唇彩 | 中心 → 外緣（漸層唇濃度）|

妝容在 canonical face model 的 **UV 空間裡定義一次**（1024² 貼圖），執行時用追蹤到的 898 個三角形變形貼到當下這張臉，所以不需要為每種臉型各畫一套。

口腔與眼球的孔洞是**從索引緩衝把三角形整個排除**，不是在貼圖上挖洞 —— 標準模型是閉眼閉嘴的中性臉，內唇與眼瞼在 UV 空間幾乎重疊，一張嘴那些三角形就被拉開，貼圖會糊到牙齒上。

### 實測

假相機（把真人臉做成 MediaStream 餵進真正的 `arLoop`）跑出來：**120 fps，追蹤 10.3 ms**，三層（唇／眼影／腮紅）都正確跟隨臉部。

貼圖只在參數真的變動時重建 —— 每次 `setMakeup` 會重畫兩張 1024²，每幀做會很貴，所以用參數簽章比對。

## 為什麼把價格搬到最後

原本 Step 3 就叫「商品推薦」，一進去就是價格、庫存、加入購物車。這有個問題：
**人一看到價格，注意力就從「好不好看」跑到「值不值得」**。而這台機器的說服力來自
前者 —— 它唯一能做而型錄做不到的事，就是讓人看見自己戴上這個顏色的樣子。

現在的順序是：

| | 談什麼 | 不談什麼 |
|---|---|---|
| Step 3 | 妝容配方：品牌、色號、質地、為什麼推薦這支 | 價格、庫存、購物車（連色號按鈕的 tooltip 與推薦理由裡的「庫存偏低」都一併拿掉）|

| Step 5 | 體驗報告 → 推薦商品（價格／庫存／加入購物車）→ 回饋 | — |

## 上妝掃掠：讓「正在被畫上去」這件事看得見

原本的上妝動畫是整張臉一起淡入。淡入解決了「察覺不到變化」，但它不像化妝 ——
真正化妝有順序：眼影、腮紅、最後口紅。

臉部 UV 的排列剛好幫了忙：

| 部位 | UV 的 v |
|---|---|
| 眉骨 | 0.28 |
| 眼皮 | 0.36 |
| 顴骨 | 0.48 |
| 唇 | 0.69 |
| 下巴 | 0.95 |

**由上往下的一道掃掠，天然就是「眼影 → 腮紅 → 唇彩」的真實上妝順序。**
所以不需要為每個區域各做一張遮罩，著色器裡多一個 `uSweep` 就夠：

```glsl
cover = 1.0 - smoothstep(uSweep, uSweep + 0.13, vUV.y);   // 掃過的地方才顯色
float d = (vUV.y - uSweep) / 0.05;
glow = exp(-d * d);                                        // 刷頭前緣的亮邊
made += vec3(glow * 0.28);
gl_FragColor = vec4(made, m.a * uAlpha * max(cover, glow * 0.8));
```

`uSweep` 從 0.28 走到 0.86，900 ms。緩動函數用 **smoothstep 而不是 easeOut** ——
easeOut 前三分之一就掃完整張臉，三個部位擠在同一瞬間出現，等於沒有順序。

**量測驗證**（逐幀比對與素顏的差異像素、取 y 重心）：

| 時間 | 變化像素 | y 重心 |
|---|---|---|
| 333 ms | 0 | — |
| 448 ms | 100 | 249（眼／頰） |
| 557 ms | 658 | 316（唇） |
| 889 ms | 701 | 317（完成） |

重心確實由上往下移動。眼影區「被偵測到」的時間比理論值晚約 200 ms，因為它的
alpha 只有唇彩的 1/4，覆蓋率還低的時候色差跨不過偵測門檻 —— 這是量測的下限，
不是動畫的錯。順帶把眼影 55→64、腮紅 42→50，這兩層原本淡到幾乎量不出來。

## 打分打的是「契合度」，不是「好不好看」（Step 5）

企劃書 Step 5 寫的是「給予 AI 的正面回饋」。我沒有做成無條件稱讚，
也沒有做成「評價這張臉」—— **打的分數是契合度：這組妝跟三個客觀對象合不合。**

這個選擇有實際理由：**契合度是可以修的，「好不好看」不是。**
說「你 71 分」很冒犯而且沒有用；說「配色契合 32°，換一顆接近唇色的腮紅」
是使用者當場就能照做的事。也因此分數低的時候必須照實說。

| 分項 | 怎麼算 |
|---|---|
| 膚色契合 | 三件商品的 `tone` 與偵測到的底調一致 = 1，中性 = 0.6，相反 = 0.25 |
| 配色契合 | 唇彩與腮紅**商品色**的 Lab 色相差；`100 − Δh × 1.7` |
| 強度契合 | 上妝幅度 ΔE 與這個妝容自己設定的強度的距離 |

契合度 = 膚色 0.40 + 配色 0.32 + 強度 0.28，再分成
**高度契合 ≥85 / 美妝契合 ≥70 / 部分契合 ≥55 / 契合度偏低**。

分級門檻要跟算法對齊：三件全吻合才是 100，摻一件中性色就掉到 87。
原本「全部吻合」的文案門檻設在 85，於是出現「87 分」配「三件都吻合」的畫面 ——
分數說 87、文字說全部吻合，等於自己拆自己的台。已改成 95。

### 兩個容易搞混的 ΔE

- **上妝幅度** = ΔE(上妝後的唇, 素顏的唇) —— 妝把唇色改變了多少
- **存在感** = ΔE(上妝後, 膚) − ΔE(素顏, 膚) —— **比素顏多出來的**唇/膚對比

第二個的減項不能省。素顏的唇本來就跟臉頰差 ΔE 約 30，直接拿絕對值當門檻，
每個人都會被判成「強烈」。實測這張臉素顏是 29.8。

實測兩個妝容，結果確實分得開：

| 妝容 | 契合度 | 膚色 | 配色 | 上妝幅度 | 存在感 | 判定 |
|---|---|---|---|---|---|---|
| 復古氣質妝 | 91　高度契合 | 100 | 16° | ΔE 18.7 | ΔE 17.9 | 明顯 |
| 自然偽素顏 | 71　大致契合 | 87 | 32° | ΔE 6.3 | ΔE 3.8 | 偽素顏 |

## 依「上妝結果」的延伸推薦

最後一段推薦不是再列一次商品，而是**根據這次實際上出來的效果**排序。

關鍵是先量出**有效覆蓋率 α**：

```
上妝後 ≈ 素顏 + α · (商品色 − 素顏)
```

把 (上妝後 − 素顏) 投影到 (商品色 − 素顏) 上就得到 α（實測 0.24）。有了 α 就能
預測「換成另一支色號，上到**這張唇**上會變成什麼樣子」，再依預測值排序：

- **最接近這次的效果** — 預測色與現在的 ΔE 最小
- **想更有存在感** — 預測色與膚色的對比最高
- **想更淡一點** — 對比最低

**為什麼不能直接比色卡**：皮膚會透出來，α 只有 0.24。色卡上差很多的兩支，
上到唇上可能幾乎一樣；反過來也有。拿色卡排序會給出看起來合理、實際上錯的建議。

覆蓋率低的時候換色號的差異本來就小，門檻設死會讓整欄空著，所以找不到明顯更濃／
更淡的就退而給極值那一支，文案裡把差多少寫出來。同一支不會同時掛兩個標籤。

### 又是同一個坑

`$${p.price}` 這次是被 **`String.prototype.replace`** 吃掉的 —— 替換字串裡的
`$$` 是「一個字面 `$`」的跳脫寫法。上一輪是模板字串吃掉，這一輪是 replace 吃掉，
症狀一模一樣：語法合法、建置不報錯、只有價格少一個錢字號。
補丁腳本現在一律用 `split().join()`。

### 兩個設計決定

**一、資料層不存翻譯後的字串，只存 key。**

`analysis.js` 判斷出暖色底調時回傳的是 `'warm'`，不是「暖色調」；警語回傳 `'warn.deep'`，
不是那句話本身。分析邏輯不應該知道畫面說什麼語言 —— 這也讓 `test.mjs` 測的是判定結果，
不是某個語言的字面。

商品名與妝容名是刻意的例外：那是資料本身，直接在 `products.js` 帶欄位。

```js
{ id: 'L307', brand: 'AURA',
  name:  '絲絨霧感唇膏', name_en:  'Velvet Matte Lipstick', name_ja:  'ベルベットマット リップ',
  shade: '#307 冷調正紅', shade_en: '#307 Cool True Red',    shade_ja: '#307 クールトゥルーレッド', … }
```

推薦理由則存成 `['reason.finish', { finish: 'matte' }]` —— key 加參數，
而且參數本身還是 key（`matte` 要先翻成「霧面 / Matte / マット」再代進去）。

**二、切換語言時整頁重繪，不做局部更新。**

畫面上大量節點是 JS 產生的（妝容卡、商品列、契合度、報告、回饋標籤）。維護兩套更新路徑
—— 靜態 `data-i18n` 一套、動態節點一套 —— 遲早會漏掉一處。重繪唯一要小心的是狀態，
而 `S` 完全不動，所以照片、選定妝容、購物車、試妝計時全部留著。

### 驗收方式

切到英文跑完整條流程，然後掃描 `#stage` 底下所有可見文字節點與 `title` 屬性裡的

| `--ink-3` `#a08b95` → `#826a76` | 3.09 → 4.78 |
| `--gold` `#b3854f` → `#9c7340` | 3.20 → 4.14 |

**二、疊在照片上的字不能跟著變淺。** 提示、`LIVE AR` 膠囊、BEFORE/AFTER 標籤
是壓在相機畫面上的，底下是什麼顏色不由介面決定。這些一律維持深色膠囊
（`--onImage`）配白字。Step 1 的取景提示原本是白字加陰影，在亮背景上還是讀不清楚，
也改成膠囊。

### 順手修掉的兩處寫死中文

`content:'素顏 BEFORE'` 和 `content:"推薦"` 直接寫在 CSS 裡，切英文日文時不會變。
改成 `content:attr(data-bare)` / `attr(data-rec)`，值由 i18n 寫進 dataset。
**CSS 的 `content` 是使用者看得到的文字，它一樣要進翻譯表。**

## AR 的互動：雙色對比、可拖曳的分界線、鏡下色號列

Step 4 原本只有滑桿和一個 BEFORE/AFTER 開關。三個問題：分界線固定在正中間、
只能跟素顏比、換色號要滑到看不見自己的地方。

現在鏡面正下方是三段模式：**全臉 · 素顏對比 · 雙色對比**，
下面接一排色號，看著自己的臉直接點。

### 雙色對比：一張臉上同時試兩支色號

專櫃真的會這樣試色。「剛剛那支好像比較橘」是記不住的，
**兩支同時上在同一張臉上**才比得準。

渲染器因此要支援兩層妝。原本著色器只有一個 `uSplit`（右側直接 discard），
改成一段範圍：

```glsl
uniform float uLo, uHi;
if (vScr.x < uLo || vScr.x > uHi) discard;
```

一個 uniform 對變成兩個之後，同一支程式就能畫兩趟：

```js
if (dualOn) {
  pass(tex.blend,  tex.bias,  -0.01, edge);   // 左：色號 A
  pass(tex.blendB, tex.biasB, edge,  1.01);   // 右：色號 B
} else {
  pass(tex.blend, tex.bias, -0.01, split >= 0 ? split : 1.01);
}
```

第二層有自己的 1024² 貼圖與自己的 dirty flag。**兩層都要靠參數簽章擋掉每幀重建** ——
少了 `lastSigB` 那道，雙色模式會每幀重畫兩張 1024² 畫布，幀率直接砍半。
實測雙色模式仍是 **130 fps，追蹤 9.0 ms**。

右半邊的預設色號不是隨便挑：取「與目前這支 ΔE 最大且有貨」的那支，
兩邊差最多才看得出這個功能在做什麼。

### 分界線可以拖

線本身就是把手（中間再加一顆 ↔ 圓鈕），不必去找一個小圓點。
全臉模式時按住畫面仍是「暫時卸妝」；進入對比模式後，同一個手勢改成拖線 ——
兩個手勢不會打架，因為它們不在同一個模式裡。

實測：拖到 0.50 → 線落在 0.497；拖到 0.70 → 0.697。

### 一個一定會出事的地方：離開 Step 4 要關掉第二層

第二層是渲染器的全域狀態。使用者在雙色模式下按「完成體驗」，
Step 5 的 AFTER 對照圖、Step 2 的妝容縮圖會全部變成半邊一個色號 ——
報告就不是「他實際做了什麼」了。所以 `go()` 裡離開 Step 4 就強制關掉第二層。

驗收方式是**從雙色模式進 Step 5** 與**從全臉模式進 Step 5**，
各掃描報告圖同一條像素列：

```
0.47:166,126,103   0.49:110,48,43   0.51:141,65,66   0.53:141,67,66   0.55:122,56,52
```

兩次逐位元組相同。（列內的變化是唇部漸層，不是分界。）

### 已知限制

沒有 WebGL 時會退回 2D 渲染器，**雙色模式在退路上只會顯示單色**（左邊那支）。
2D 版沒有兩層貼圖的概念，與其做一個半殘的版本，不如讓它退回可用的單色。

## 手動上妝：虛擬刷具

Step 4 的第四個模式。自動上妝把妝一次貼好，這個模式反過來 ——
**先把臉還原成素的，讓使用者自己畫。**

### 關鍵：筆觸存在 UV 空間，不是螢幕空間

這是整件事成立與否的分水嶺。畫在螢幕座標上，頭一轉妝就留在原地，
會變成「臉上有汙漬」；畫在 UV 上就等於畫在臉上，轉頭妝跟著走。

已經有 UV 網格了，剩下的只是把螢幕座標反推回 UV。用重心座標插值：

```js
// 先找點落在哪個三角形裡，再用同一組重心權重插它的三個 UV
const w0 = ((b.y-c.y)*(px-c.x) + (c.x-b.x)*(py-c.y)) / d;
const w1 = ((c.y-a.y)*(px-c.x) + (a.x-c.x)*(py-c.y)) / d;
const w2 = 1 - w0 - w1;
if (w0 < 0 || w1 < 0 || w2 < 0) continue;      // 不在這個三角形裡
```

這是精確解，不是把臉當平面近似 —— 側臉與張嘴時才不會偏掉。
點落在臉外就回傳 `null`，所以**畫不到背景上**（實測背景點回傳 null）。

手繪層是獨立的兩張 1024² 畫布（blend / bias），在 `buildTextures()` 最後疊上去。
用的是跟自動上妝一模一樣的顏色慣例，所以**著色器完全不必知道有這回事**。

### 每一筆都很淡，靠反覆塗抹堆疊

單筆 alpha 只有 `flow/100 × 0.16`。真的化妝就是這樣 —— 一次刷不出想要的濃度，
要來回幾次。滑桿從「三個部位的濃淡」換成「筆刷大小」與「濃度」。

兩個 pointer 事件之間會補點（每 6px 一筆），快速拖曳才不會畫成一串斷掉的點。

### 三個踩到的坑

**一、`object-fit: cover` 的座標換算。** AR 畫布是 4:3，外框是直式，
`cover` 會把左右裁掉。直接用 `rect.width` 當比例，點會整片偏掉 ——
筆刷第一版完全畫不上去就是這個原因。要把裁切算回去：

```js
const k = Math.max(r.width / c.width, r.height / c.height);
const px = (e.clientX - r.left - (r.width - c.width * k) / 2) / k;
```

**二、手動模式沿用了對比模式的分界線。** `setSplit(S.mode === 'full' ? -1 : S.splitX)`
—— 手動模式不是 `full`，於是 `uSplit = 0.5`，右半邊全被 discard，
畫得再認真也只有左半邊看得到。這個 bug 的症狀（「有時候畫得上去有時候畫不上去」）
特別難從畫面判斷，是靠量測落在 x=0.51 的像素才抓到的。

**三、合成事件的 `setPointerCapture` 會丟 NotFoundError**，
整個 `pointerdown` 處理直接中斷。抓不到指標不是致命錯，包 try/catch 忽略。

### 手繪層要出現在哪裡

| 畫面 | 含手繪？ | 為什麼 |
|---|---|---|
| Step 4 即時 AR | ✅ | 就是他正在畫的東西 |
| Step 5 報告的 AFTER | ✅ | 報告要反映**他做了什麼** |
| Step 2 妝容縮圖 | ❌ | 那是「這個妝容長什麼樣」，不該混進他自己畫的 |
| Step 3 商品預覽 | ❌ | 同上 |

用 `useBrush(bool)` 切換，實測回到 Step 2 後四張縮圖乾淨、頰部沒有殘留筆觸。

### 實測

同一組基底畫面、同一組關鍵點，各渲染一次比對：

| | 唇部取樣 |
|---|---|
| 素顏 | `rgb(179,118,112)` |
| 手繪後 | `rgb(157,99,94)` |
| 擦掉重來 | `rgb(179,118,112)` |

擦掉後**逐位元組回到素顏**。額頭在整個過程中沒有變化（`rgb(196,169,161)` 前後相同）。

### 已知限制

沒有 WebGL 時的 2D 退路**不支援手繪**。手繪層是 UV 貼圖的機制，2D 版沒有這個概念。

### 現場除錯

`?debug` 會把 `__LUCID_AR__`（`hasBrush` / `screenToUV` / `renderGL` / `toPixels`）
掛到 window 上。「畫不上去」有兩種完全不同的原因 ——
筆觸沒進去，或進去了但沒重繪 —— 只看畫面分不出來，這組 hook 就是為了分開它們。

## 參考輕顏相機與美圖秀秀：Step 4 操作區重組

> 我沒有辦法在這台機器上開那兩支 app，以下是依它們廣為人知的互動模式做的整理。
> 版本更新後細節可能已經不同，若要做正式的競品分析，請以實機為準。

兩支 app 的共同做法，套到櫃位機台上仍然成立：

| 它們的做法 | 這裡怎麼落地 |
|---|---|
| 妝容是**一排圓形膠囊**，縮圖就是效果本身，點一下整組換掉 | `#s4-looks`：五顆圓膠囊，縮圖是**使用者自己的臉**套上該妝容 |
| 濾鏡列開頭有一顆「无」 | 第一顆是「不上妝」，把三個部位的濃度歸零 |
| 細調收在**分頁**裡（口紅／眼影／腮紅），一次只出現一組 | `#s4-tabs`：唇彩／眼影／腮紅／手動上妝 |
| 每個分頁是「色號列 + 一條強度滑桿」 | 完全照做，並在中間補一行目前色號與質地 |
| 檢視類開關**浮在畫面上**，不佔下方版面 | 對比模式改成浮在鏡面左上角的膠囊列 |

### 改動前後

之前 Step 4 下方是四塊獨立區域堆疊：模式列、色號列、刷具列、三條滑桿。
問題不是不能用，是**三條滑桿同時攤開，人不知道要先動哪一條** ——
這正是那兩支 app 用分頁解掉的問題。

現在下方只有兩塊：妝容膠囊列 + 分頁（分頁內容自己換）。高度變短，
而且「選妝容」與「調細節」被分成兩層，不會互相干擾。

### 刻意沒有照抄的部分

那兩支 app 的核心是磨皮、瘦臉、大眼與濾鏡 —— 目標是「讓你看起來更好看」。
這台機器的目標不同：**「這支色號在你臉上是什麼樣子、多少錢、櫃上還有沒有貨」**。

所以：

- **不做任何美化臉型或磨皮的處理。** 顧客照著螢幕買了色號，回家對鏡子發現
  不是那個樣子，這台機器就再也沒有人相信了。瘦臉能讓當下的照片好看，
  卻會直接破壞它唯一的價值。
- **顏色一律來自實際商品的實測色值**，不是好看的預設濾鏡。
- **色號列裡缺貨的會變灰、點不下去**，這是專櫃的現實，濾鏡 app 沒有這個問題。

### 實測

同一組基底與關鍵點，點四顆妝容膠囊各渲染一次：

| 膠囊 | 唇部取樣 | 對應色號 |
|---|---|---|
| 不上妝 | `rgb(179,118,112)` | — |
| 復古氣質妝 | `rgb(136,63,63)` | #307 冷調正紅（濃度 92） |
| 清透通勤妝 | `rgb(150,90,86)` | #307 冷調正紅（濃度 65） |
| 自然偽素顏 | `rgb(157,103,96)` | #455 裸感奶茶 |
| 韓系微光妝 | `rgb(155,101,94)` | #455 裸感奶茶 |

前兩列是同一支色號、不同濃度，數值也確實分得開。
高亮、色號名稱、右側商品卡與 `LIVE AR` 標籤都跟著換。

### 一個測試環境的坑

Browser 面板隱藏時 `requestAnimationFrame` 會被節流到約 1 fps，
`arLoop` 幾乎不跑 —— 於是 `intensity` 與 `sweep` 會**停在上妝動畫的中途**，
量到的顏色比實際淡很多（第一次量四個妝容只差 3~4 階，看起來像壞掉）。
等 2.5 秒讓動畫跑完再量，數值才拉開。畫面上的 fps 讀數在這種情況下不可信。

## 再看一次美圖秀秀：撤銷／重做與質地篩選

上一輪主要借的是輕顏的濾鏡膠囊列。美圖秀秀是**編輯器**，不是相機，
它真正不一樣的兩件事，這台機器都缺：

### 一、撤銷 / 重做

編輯器最上面永遠有一對撤銷／重做。這台機器少了它 ——
使用者一路點色號、拉濃度、手繪，弄壞了只能整組重來。

兩種步驟混在同一個堆疊：

| 類型 | 存什麼 |
|---|---|
| `state` | 換色號、拉濃度、換妝容：前後兩份小快照（商品 id + 濃度） |
| `stroke` | 手繪的一筆：交給渲染器自己的筆觸堆疊 |

**混在一起是刻意的** —— 使用者心裡只有「上一步」，不會分那是哪一類操作。

兩個實作上的判斷：

- **筆觸不存點陣快照。** 一張 1024² 的 ImageData 是 4 MB，十步就 40 MB。
  改成記下每一筆的落點，撤銷時把剩下的筆觸重畫一遍 —— 幾毫秒的事。
- **滑桿拖曳整段算一步。** 每個 `input` 事件都記的話，撤銷會變成一格一格倒退，
  拖了五十格就要按五十次。改成 `input` 時只記起點、`change`（放開）時才入堆疊。
- **筆刷大小與濃度不進歷程。** 那是「工具設定」，不是「做過的事」；
  撤銷把筆刷變細不會是任何人的預期。

實測：

| 操作 | 結果 |
|---|---|
| 換色號 #307 → #204，撤銷 | 回到 #307；再重做 → #204 |
| 濃度 92 →（經 80/70/60/50）→ 45，放開後撤銷 | 一次回到 92（不是退回 50） |
| 手繪兩筆，撤銷兩次 | `hasBrush()` 由 true 變 false |
| 「擦掉重來」 | 連帶把堆疊裡的 `stroke` 步驟清掉 —— 筆觸都沒了，那些步驟不該還能撤銷 |

### 二、質地篩選

美圖秀秀的口紅面板是**先選霧面／水光／珠光，再挑色號**。
「我只要霧面」是買東西時真的會有的條件，而這裡剛好對得上商品既有的 `finish` 欄位。

色號列上方多一排 `全部 · 霧面 · 水光 · 珠光`，只列出該類別實際有的質地
（唇彩沒有珠光品項，那顆就不會出現；只剩一種質地時整排隱藏，不做沒有選擇的選擇題）。

### 沒有照抄的：×／✓ 的commit 流程

美圖秀秀進二級面板後，右下角是一對「取消／套用」，改動要確認才生效。
那是**檔案編輯器**的語彙 —— 有一份文件要存。

這台機器沒有文件。每個改動本來就即時反映在鏡子裡，再加一層「確認」只會多一次
沒有意義的點擊，而且會讓人以為「還沒按套用所以現在看到的不算數」。
有了撤銷之後，取消鍵要解決的問題已經被解掉了。

## Step 5 修圖：加在 AR 之後、報告之前

> **已移除（2026-09-11）**：流程調整為四步時拿掉了，見〈流程調整為四步〉。以下保留當時的設計紀錄。

參考美圖秀秀的編輯器：**濾鏡預設列 + 分頁（調色 / 裁切）+ 撤銷重做**，
結構跟 Step 4 刻意做成一樣 —— 使用者只要學一次。

進入這一步時把 Step 4 當下的畫面拍下來，之後所有編輯都在這張上面做。

| 分頁 | 內容 |
|---|---|
| 調色 | 亮度 · 對比 · 飽和 · 色溫 · 暗角，五條雙向滑桿（0 在正中間）＋ 全部歸零 |
| 裁切 | 原比例 · 1:1 · 4:5 · 9:16，置中裁切 |
| 預設 | 原圖 · 清透 · 暖陽 · 膠片 · 黑白，縮圖一律方形（比的是調色，不是構圖）|

按住畫面看原圖、撤銷／重做都跟前面一致。

### 這一步的界線：修圖不能碰量測

**Step 2 的膚色分析、Step 4 的 AR、Step 6 的契合度與 ΔE，走的一律是未經修圖的合成畫面。**
修圖只作用在「要帶走的那張照片」上。

理由很直接：前面花了很多力氣讓顏色可信 —— 眼白白平衡、商品照 ΔE 檢查、螢幕校色 ——
如果讓一條「飽和度 +40」的滑桿回頭汙染量測，那些全部白做。
**修圖是紀念品，不是量測。**

實作上這是靠來源分離達成的：`retouch.js` 只吃 `S.shot`（Step 4 的截圖），
產出 `S.edited`；報告那一路完全不經過它。

驗收方式是套上最重的預設（膠片 + 4:5 裁切）進報告，再回頭改成原圖進報告，
比對報告圖同一條像素列與契合度分數：

```
166,126,103 | 110,48,43 | 141,65,66 | 141,67,66 | 122,56,52     契合度 91
```

兩次完全相同。

### 調色的算法

在 sRGB 值域直接算 —— 這是外觀調整，沒有必要（也不該）假裝它有色度計算上的嚴謹性：

```js
r = data[i] * kb * kr;                     // 亮度、色溫（R 加、B 減）
r = (r - 128) * kc + 128;                  // 對比繞中灰
const y = 0.2126*r + 0.7152*g + 0.0722*b;  // Rec.709 亮度
r = y + (r - y) * ks;                      // 飽和度沿灰軸拉伸
```

暗角用徑向漸層疊上去，不逐像素算 —— 效果一樣，成本差一個數量級。

### 實測

| | 臉頰 | 唇 | 左上角 |
|---|---|---|---|
| 原圖 | `176,145,130` | `134,62,62` | `32,48,63` |
| 膠片 | `176,145,130` | `122,54,53` | `19,31,42` |

臉頰那一格兩者相同不是 bug —— 膠片的 `亮度 −4 / 對比 +18 / 飽和 −18 / 色溫 +8`
套在這個膚色像素上剛好互相抵消（手算是 176,145,129）。
換到唇部與角落就分得很開，暗角也確實壓下去了。第一次量只取臉頰一點，
差點把「取樣點選得不好」誤判成「預設沒生效」。

裁切：640×480 → 1:1 得 480×480、9:16 得 270×480。

### 一樣沒有做的：磨皮與瘦臉

美圖秀秀的核心功能之一，這裡仍然不做，理由跟前面一致：
顧客照著螢幕買了色號，回家對鏡子發現不是那個樣子，這台機器就沒有人相信了。

修圖這一步之所以可以存在，正是因為它**明確地不在量測路徑上** ——
它調的是要帶走的照片。磨皮瘦臉如果做進 Step 4 的即時畫面，性質就完全不同了。

## 單檔版 Step 5 整步驟啞掉：同一個坑踩第二次

現場錄影回報「第 4 步跟第 5 步有問題」。Step 5 的畫面是**整片空白的灰底**，
濾鏡列、調色／裁切分頁、滑桿、撤銷重做全部沒有出現，
而底下的按鈕還停在 Step 4 的「換妝容 / 完成體驗」。

最後那一點是關鍵線索。`enter5()` 的順序是

```js
mountPresets(); mountEditTabs(); mountEditPanel(); mountEditHist();
bindEditHold(); paintEdit();
setActions([...]);          // ← 最後才換按鈕
```

按鈕沒換掉，代表 `enter5()` **在跑到 `setActions` 之前就丟例外中斷了**。
畫面上看起來像「照片沒載入」，實際上是整個步驟從第一行就死了。

**成因**：`js/app.js` 的

```js
import { PRESETS, RATIOS, ZERO, render as renderEdit } from './retouch.js';
```

`build.mjs` 併模組時會把整行 `import ... from './…'` 剝掉。
非別名的匯入沒事（`PRESETS` 等等本來就是頂層宣告，併進同一個 scope 就找得到），
但 `renderEdit` **從來沒有被宣告過** —— 它只是 `render` 的別名，而別名跟著 import 行一起消失。
於是 `mountPresets()` 的第一次呼叫就丟 `ReferenceError: renderEdit is not defined`。

只有單檔版與靜態站台會中招，`node server.js` 的開發版走真正的 ES 模組，別名是有效的 ——
**所以本機怎麼測都是好的，只有交出去的那個檔案壞掉**，這也是它一路活到現場的原因。

**修法**

1. `js/retouch.js` 的 `render` 直接更名為 `renderEdit`，`app.js` 改成非別名匯入。專案裡沒有第二個頂層 `render`，不會撞名。
2. `build.mjs` 補上真正的別名匯入偵測（上一輪只寫在 README 上，程式沒寫）。掃到就中止：

```
建置中止：有別名匯入，import 行被剝掉後別名就不存在了
  js/app.js  import { renderEdit as reGrade } —— 打包後 reGrade 不存在
```

**驗收**：單檔版載入後 `typeof renderEdit` 由 `undefined` 變成 `function`；
`grep -c renderEdit lucid-demo.html` 由 2（兩次呼叫、零定義）變成 3（一個定義、兩次呼叫）。
走完整條流程到 Step 5，`#edit` 是 640×480、中心像素 `rgb(168,134,113)`（膚色，不是空白），
濾鏡 5 顆、分頁 2 個、面板 6 列，按鈕是 Step 5 自己的「重拍這張 / 看體驗報告」。

### 順手修掉的兩件事

**手動上妝時有兩排一模一樣的按鈕。** `TABS` 與 `BRUSH_TOOLS` 用的是同一組
i18n 鍵（`sl.lip` / `sl.eye` / `sl.cheek`），所以進入手動上妝後畫面上會出現

```
唇彩  眼影  腮紅  手動上妝     ← 現在調哪個部位
唇彩  眼影  腮紅  擦掉重來     ← 筆刷塗在哪個部位
```

字面與色點完全相同、語意卻相反（點上排的「唇彩」是離開手動模式，點下排的是換筆刷目標）。
第二排前面加了「塗在」的前綴標籤把兩者分開。

**置中的 flex 溢出時左側會被切掉而且捲不到。** `#stage` 是
`display:flex; justify-content:center`，`body` 又是 `overflow:hidden`；
`#mirror` 的寬度是由「高度 × `aspect-ratio`」推導出來的，視窗又高又窄時
它加上右側 300px 商品卡就可能超出視窗寬 —— 溢出的部分會被**左右各切掉一半**，
而且因為沒有捲軸，左邊那一半永遠拿不回來。Step 5 剛好把商品卡藏起來，所以只有
Step 3 / 4 / 6 會中。兩道防線：

- `justify-content:safe center`：一旦溢出就退回 `flex-start`，左側絕不會被切掉。
- 橫排且商品卡在場時，再用可用寬度把 `#mirror` 的高度夾一次，讓它根本不會溢出。

## 筆壓：把「畫得輕」跟「沒畫到」分開

手動上妝原本每一筆的濃度都一樣，只能靠反覆塗抹堆疊。真實刷具不是這樣 ——
輕輕帶過就是薄薄一層，壓下去才會實。這一輪把 `PointerEvent.pressure` 接進去。

接的位置很單純：`brushDab(u, v, o)` 本來就是**每一點各自帶著自己的 `o`**，
所以筆壓只要在 `o` 上乘一下就好，撤銷重播（`replay()` 逐點重跑 `stamp`）
天然就會保留當初的力道，不需要另外存。

### 一、不能直接相信 `e.pressure`

規格規定：**不支援壓力感應的裝置，按下去回 0.5、放開回 0**。

所以 0.5 有兩種完全不同的意思 —— 「使用者用一半的力」與「這台裝置根本沒有壓力感應」。
直接拿來乘，**所有滑鼠使用者的妝會無緣無故淡掉一半**，而且沒有任何線索告訴他為什麼。

判定規則因此分成三種指標裝置：

| `pointerType` | 怎麼處理 |
|---|---|
| `mouse` | 一律滿壓。滑鼠沒有壓力感應，這不需要偵測 |
| `pen` | 直接相信。觸控筆幾乎都有真正的壓力值 |
| `touch` | **要先真的看到「不是 0 也不是 0.5」的值**才承認 |

第三列是關鍵：一般電容式觸控螢幕固定回 0.5 或 1，力度觸控螢幕與 Apple Pencil
才會回變動值。在還沒量到變動值之前一律滿壓 —— **寧可沒有筆壓，也不要讓所有人的妝莫名其妙變淡。**

而且量到的結果要**照實說**。畫完一筆仍然沒量到筆壓，面板上就會多一行：

> 這台裝置回報不了筆壓（滑鼠或一般觸控螢幕都沒有壓力感應）—— 濃淡請用上面的「濃度」。要有筆壓得接觸控筆。

不寫出來的話，使用者只會以為是自己壓得不夠用力。

### 二、曲線不能是線性的

原始值線性對應到濃度太鈍：0.1 的力道只有 0.10 的濃度，等於白畫。
改用 `p^0.65`，0.1 的力道還有 **0.22** 的濃度 —— 輕壓要看得見，那才叫「畫得輕」。

濃度與半徑的乘法刻意不一樣：

| | 隨筆壓變化 | 為什麼 |
|---|---|---|
| `alpha` | 1.0 → 0（線性乘 k）| 濃淡是筆壓的主要表現 |
| `radius` | 1.0 → 0.62 | 真實刷毛壓下去會散開，但如果半徑也歸零，輕壓會變成一個又小又淡的點，看起來像「沒畫到」而不是「畫得輕」 |

`bias`（珠光的加性補光）不另外乘 —— `stamp()` 裡它本來就是 `alpha × bias`，
濃度乘下去珠光自然跟著淡，再乘一次就會變成平方。

### 三、筆壓要跟座標一起內插

原本兩個 pointer 事件之間就會補點（快速拖曳才不會畫成一串斷掉的點）。
如果補出來的點全部沿用事件當下那一個壓力值，**快速加壓時中間會出現一條肉眼看得到的硬邊**。
所以 `qk` 跟 `qx`／`qy` 用同一個 `t2` 一起內插。

### 四、關得掉

面板多一條「筆壓」滑桿（預設 65）。**拉到 0 必須「完全等於」沒有筆壓這回事**，
不是「影響很小」—— 櫃位機台大多是一般觸控螢幕，留一個關得掉的開關比硬套一條曲線誠實。
`pressureLevel(raw, 0)` 對任何 `raw` 都回 `1`，`test.mjs` 有一組專門驗證這件事。

### 實測

`test.mjs` 第 12 組驗證純函式（不支援時回滿壓、靈敏度 0 等於關閉、單調遞增、
滿壓等於滑桿設定值、輕壓仍有 0.22、半徑不會跟著歸零、bias 不被重複乘）。

瀏覽器端用合成的 `pointerType:'pen'` 事件，同一條唇部路徑各畫 8 筆（濃度 100），
量唇部包圍盒平均色與素顏的距離：

| 筆壓 | 與素顏的色差 | 相對滿壓 |
|---|---|---|
| 0.12 | 4.54 | 0.39 |
| 0.35 | 6.76 | 0.58 |
| 0.65 | 9.16 | 0.79 |
| 1.00 | 11.63 | 1.00 |

三組回歸（同樣 8 筆、同一條路徑）確認既有行為沒被動到：

| 情境 | 色差 |
|---|---|
| 觸控筆 · 滿壓 · 靈敏度 65 | 11.61 |
| **滑鼠 · `pressure` 回 0.5** · 靈敏度 65 | **11.59** |
| **觸控筆 · 輕壓 0.12 · 靈敏度 0** | **11.67** |
| 觸控筆 · 輕壓 0.12 · 靈敏度 65 | 4.55 |

中間兩列跟第一列在量測誤差內相同 —— 滑鼠使用者與把筆壓關掉的機台，行為與加筆壓之前一致。

### 現場除錯

`?debug` 的 `__LUCID_AR__` 多掛了 `pressureLevel`、`applyPressure` 與
`press()`（回報 `{ seen, sens }`）。「筆壓好像沒作用」有兩種原因 ——
裝置沒回報，或回報了但靈敏度設太低 —— `press().seen` 一看就分得出來。

> 量測時注意：`?debug` 會把 478 個關鍵點畫在畫布上，直接取樣關鍵點座標會量到那些圓點
> 而不是妝。上面的數據是取唇部外輪廓包圍盒的**平均色**，圓點在各組之間是同一組常數，
> 會被差值抵消掉。

## Step 4 模式切換卡死：鏡面手勢吃掉了按鈕的點擊

現場錄影：進入「素顏對比」之後，再點「全臉」或「雙色對比」都沒反應，高亮一直停在素顏對比。
而且**每點一次，分界線就跳到游標所在的位置** —— 點最左邊的「全臉」時，線直接被拉到畫面最左緣。

最後那個現象就是答案：按按鈕的動作被當成了「拖分界線」。

模式切換（`#s4-mode`）與撤銷／重做（`#s4-hist`）是**浮在鏡面上**的，DOM 上是 `.frame` 的子元素。
按它們時 `pointerdown` 會冒泡到鏡面，而對比模式下鏡面的處理是：

```js
e.preventDefault();
frame.setPointerCapture(e.pointerId);   // ← 關鍵
moveTo(e);                              // 分界線跳到游標那裡
```

`setPointerCapture` 之後，放開時的 `click` 會被改派給**鏡面本身**，按鈕的 `onclick` 永遠不會觸發。
全臉模式走的是「按住卸妝」，不做 pointer capture，所以從全臉**進得去**對比模式，卻**出不來** ——
這就是「只能單向切換」的原因。手動上妝模式下點撤銷也會中同一個坑（會變成開始畫一筆）。

**修法**：`onControl(e)` 判斷指標是不是按在 `button / input / select / a` 上，是的話鏡面手勢直接讓開。
套在三個地方：Step 4 鏡面（按住／拖線／手繪）、Step 2 與 Step 5 的按住看素顏。

**驗收**必須用**真實的指標事件**。用 `button.click()` 會直接繞過 pointerdown，永遠測不出這個 bug。
在 583×726 的視窗用滑鼠實點：

| 操作 | 結果 |
|---|---|
| 全臉 → 素顏對比 | ✓ |
| **素顏對比 → 全臉**（原本失敗） | ✓ |
| 素顏對比 → 雙色對比 | ✓ |
| 雙色對比 → 全臉 | ✓ |
| 素顏對比下拖曳鏡面 | 分界線照常跟著移動（沒有被這道判斷擋掉） |

## 雙色對比「看不出效果」：分界線要跟著臉走

現場回報雙色對比沒有效果。先量渲染本身 —— **它其實有作用**：

| | 分界線左半邊唇色 | 右半邊唇色 |
|---|---|---|
| 全臉（兩邊都是 #307） | `125,69,56` | `130,62,56` |
| 雙色對比（左 #307、右 #455） | `125,69,56`（不變） | `137,78,68`（換了） |

那為什麼看不出來？查了兩個懷疑，一個成立、一個不成立。

### 不成立的：預設的 B 挑錯了

B 預設挑「跟 A 色差最大、有貨」的那支，從 #307 冷調正紅挑到的是 #455 裸感奶茶。
裸色上到嘴唇上最不明顯，看起來像是挑錯了。實際把每一支有貨的色號都當 B 量一次
（拖分界線讓整片唇只有 B，素顏唇色 `156,94,81`，素顏→A 是 ΔE 12）：

| B | A↔B（ΔE） | 素顏→B（ΔE） |
|---|---|---|
| #204 蜜楓棕 | 3.4 | 10.6 |
| #118 玫瑰豆沙 | 3.5 | 9.8 |
| #512 蜜桃汽水 | 5.9 | 6.4 |
| **#455 裸感奶茶（預設）** | **6.8** | 6.9 |

**#455 已經是差最多的那支。** 有貨的色號上到嘴唇之後彼此最多只差 ΔE 7 左右 —— 唇膏會跟原本的唇色混在一起，
這跟〈依「上妝結果」的延伸推薦〉那一節是同一件事：色卡差很多，上到唇上可能幾乎一樣。
這是照實呈現的結果，**沒有為了讓對比明顯而把顏色加濃**，那會讓試色失真。

### 成立的：分界線固定在畫面正中間

分界線原本是「畫布寬度的 50%」，跟臉在哪裡無關。連假鏡頭都沒對準 —— 唇部被切成 264 px 對 1029 px，
**左 20%、右 80%**。真人站得稍微偏一點，整張臉就落在同一側，只看得到一支色號，雙色對比就等於沒開。

改成**記住相對臉中線的偏移**（`S.splitOff`），每一幀用臉中線加上偏移算出分界線：

- 臉中線取鼻樑、鼻尖、上唇、下唇（168 / 1 / 0 / 17）四點的平均，頭稍微轉也穩
- 拖曳改寫的是偏移量，所以拖完之後人移動，線仍然跟著臉走
- 每次切進素顏對比或雙色對比，偏移歸零 —— 線從臉的中線出發

修正後同一個畫面，唇部被切成 **831 px 對 769 px（52% / 48%）**。素顏對比也一起受惠。

## 介面設定：配色與圓角

頁首多一顆齒輪，打開是設定面板：

- **配色**：玫瑰粉（預設）、香檳金、薰衣草、鼠尾草、霧藍
- **圓角**：柔和（預設）、俐落（只改三個圓角變數，版面尺寸完全不變）

選擇存在 `localStorage`，模組一載入就套用 —— 開機畫面就是選好的配色，不會先閃一下粉紅。
語言切換時面板會跟著重掛，三語系都有。點面板以外的地方就收起來。

### 一條不能讓步的規則：只換外框

三樣東西刻意**不跟著配色走**：影像框的中性灰（`--neutral`）、商品色票、AR 上妝顏色。
這跟〈影像框一律中性灰〉是同一個理由 —— 綠色或紫色包圍一樣會把口紅顏色看偏，
而整台機器的價值來自「顏色可信」。面板底下也把這件事寫給使用者看。

### 做法：先把寫死的粉紅抽出來

只換 `:root` 的變數是不夠的 —— `main.css` 裡有大量寫死的粉色系（選中狀態的淡底、各種投影、
主要按鈕的漸層）。第一次只抽了出現次數多的，切到鼠尾草時**主要按鈕還是粉紅色**；
第二次逐一掃過所有「非中性」的寫死顏色才補齊。

抽出來的變數預設值就是原本寫死的值，**預設的玫瑰粉外觀逐值不變**。剩下沒抽的寫死顏色都是刻意的：
綠色 OK 提示、紅色錯誤框、點亮的金色星星（顏色本身有意義），CSS 畫的口紅管與眼影盤（那是商品的樣子），
「不上妝」膠囊的膚色（它代表素顏）。

## AR 顏色還原：從「染色濾片」改成「顏料層」

需求：加強 AR 上妝的顏色，盡可能還原化妝品本身的顏色效果。先量、再改、再量。

### 問題：每一支唇膏上唇後都變成同一種暗紅

新增的 `_color.html`（色彩還原量測台）把每一支唇色上到同一張臉上，量四件事：

- **像不像色卡**：取唇部亮度中段（素顏的第 25–85 百分位，避開陰影與高光），用眼白增益去掉環境光，換成「反射率顏色」，再跟色卡算 ΔE2000
- **與預期混合色的差**：覆蓋率 c 下應該看到 c·商品 + (1−c)·原本唇色。水光這種透明質地用這一欄判斷才公平
- **色號區辨保留率**：上唇後的兩兩色差 ÷ 色卡上的兩兩色差。1 = 色卡上的差異完整保留
- **紋理保留**與**唇以外有沒有被動到**

舊模型的結果：霧面唇膏上唇後與色卡平均差 **ΔE00 12.8**，色號之間的差異只剩 **39%**。
放大圖一看就懂 —— #512 蜜桃汽水（珊瑚橘）變成棕色、#307 冷調正紅變成暗酒紅、#455 裸感奶茶只是唇色變暗，
六支全部是深淺不同的「暗紅棕色唇」。

原因在著色器的合成式 `made = skin × 商品色`，而且是在 sRGB（gamma 編碼）裡乘：

1. **乘法是「透明染料濾片」的物理。** 唇膏、眼影、腮紅是顏料層，看到的是顏料的反射率乘上當下的光，
   不是皮膚的顏色再被乘一次。乘法把唇本身的紅算了兩次，所有色號都被拉向同一種暗紅。
2. **在 gamma 空間裡做乘法與混合。** 光的疊加必須在線性空間算。

之前〈雙色對比「看不出效果」〉量到「有貨的色號上到唇上彼此最多只差 ΔE 7」，當時以為是唇膏和唇色混在一起的必然結果 ——
**其實大半是這個模型造成的。**

### 新模型：線性空間的反射率取代

著色器（`js/makeup-gl.js` 的 `FS`）現在這樣算：

1. 相機值轉成**線性**，乘上眼白估出的三通道增益 → 去掉環境光的**反射率**
2. 反射率亮度 ÷ 該區域的平均亮度 = 這一點的**明暗 s**（受光面 > 1、陰影 < 1）
3. 妝 = **商品反射率 × s** —— 底色換成商品，明暗與紋理原樣保留
4. 依**覆蓋率**跟原本的反射率混合，除回增益、編回 sRGB
5. **水光**：受光面加一層光源色的鏡面反射；**珠光**：受光面帶商品色的光澤，加上固定在 UV 上的細閃（頭一轉閃點跟著皮膚走）

混合全部在著色器裡做，不再交給 GL 的 alpha blending（那是在 sRGB 裡混）。沒上妝的像素直接 `discard`，一個位元都不改。

**覆蓋率由質地決定**（`COVERAGE`，App 與量測台共用的單一來源），再乘上使用者的濃度滑桿：

| | 霧面 | 水光 | 珠光 |
|---|---|---|---|
| 唇 | 0.92 | 0.62 | 0.72 |
| 眼影 | 0.62 | 0.50 | 0.55 |
| 腮紅 | 0.42 | 0.35 | 0.38 |

霧面唇膏顏料含量高、幾乎不透；水光唇釉是透的，看得到一部分原本的唇色；眼影可疊擦但單次不會全蓋；腮紅是刷開的薄霧。

**兩個亮度基準**（唇、皮膚）是明暗 s 的分母，由 `renderGL` 每 8 幀從「還沒上妝」的畫面重量一次，並平滑處理 ——
基準一跳，整片妝就會跟著閃。在照片上渲染（Step 2 縮圖、產品頁預覽、評價頁對照圖）與進入 AR 時會先 `resetRefs()`，
不沿用別張圖的基準。

**光線**：Step 2 用拍照那張的眼白增益（取樣不可信時用 1，不補償）；AR 裡每秒用即時畫面的眼白重估一次，
以 30% 小步混合進去 —— 櫃位燈光、使用者轉身都會改變照在唇上的光，但不能讓整片妝一次跳色。

`bias` 貼圖不再存顏色，改存「這裡是什麼材質」：r = 水光、g = 珠光、b = 是不是唇。手動上妝的筆觸也用同一套編碼。

### 結果

兩張臉：專案裡的假鏡頭臉，以及一格真人錄影（辦公室燈光、真實的相機；只在本機量測時用 `?img=` 帶入，沒有放進專案）。

| | 假鏡頭臉：舊 → 新 | 真人臉：舊 → 新 |
|---|---|---|
| 霧面唇膏與色卡 ΔE00 | 12.8 → **1.1** | 11.2 → **1.1** |
| 全部色號與色卡 ΔE00 | 13.6 → **3.1** | 12.9 → **3.0** |
| 與預期混合色 ΔE00 | — → **1.2** | — → **0.4** |
| 色號區辨保留率 | 39% → **79%** | 35% → **77%** |
| 紋理保留 | 83% → 116% | 88% → 114% |
| 唇以外 ΔE00 | 0 → 0.01 | 0 → 0 |

ΔE00 小於 2 肉眼幾乎分不出來 —— 霧面唇膏上唇後已經跟色卡非常接近。逐支（假鏡頭臉，新模型）：

| 色號 | 質地 | 覆蓋率 | 與色卡 | 與預期混合 |
|---|---|---|---|---|
| #204 蜜楓棕 | 霧面 | 0.92 | 1.1 | 0.7 |
| #118 玫瑰豆沙 | 霧面 | 0.92 | 0.8 | 0.9 |
| #307 冷調正紅 | 霧面 | 0.92 | 1.3 | 0.6 |

| #455 裸感奶茶 | 水光 | 0.62 | 2.0 | 1.3 |

**#620 與色卡還差 9.9 是對的**：它是水光，覆蓋率 0.62，本來就會透出底下較淺的唇色；跟預期混合色只差 2.6。

**App 裡的實測**

| 檢查 | 結果 |
|---|---|
| 雙色對比左右差（#307 / #455） | ΔE 7.3 → **24.3** |
| 渲染成本 | 每幀 **1.91 ms**（亮度基準每 8 幀重量）；最壞情況每幀都重量 8.2 ms。30 fps 的預算是 33 ms |

> 量到的會是同一張圖，看起來像「按住沒反應」「塗了沒顏色」。上面的功能檢查是繞過 AR 迴圈，直接從鏡頭取一格素顏畫面呼叫 `renderGL`。

### 還沒解決的與限制

- **覆蓋率表是工程估計，不是量出來的。** 下一步應該拿實品在真人唇上、D65 光源、放一張色卡拍照，逐支擬合覆蓋率與水光強度。
  量測台已經能算「與預期混合色的差」，換成實拍照片就能直接用。
- **商品色準不準，取決於 `products.js` 的色值本身。** 渲染器能把色值忠實地上到唇上，但色值如果跟實品有落差，結果就跟著偏
  （見〈真實商品照〉的色彩檢查）。
- **眼白取樣不可信時增益退回 1**，等於信任相機自己的白平衡。那格真人影格就是這樣（臉在畫面裡偏小）。
- **紋理保留超過 100%**：水光的鏡面高光增加了明暗起伏，不是被塗平；但對比略強一點。
- 水光鏡面與珠光細閃是**外觀近似**，不是物理量測。
- 沒有 WebGL 時的 2D 退路（`makeup.js`）仍是舊模型。

### 眼影與腮紅

眼影、腮紅是半透明的，沒有「應該等於色卡」的標準答案。量測台檢查的是「有上色」與「顏色往商品色的方向走」
（a*b* 平面上，上妝造成的位移與「素顏 → 商品色」方向的夾角餘弦，1 = 完全同方向）：

| | 腮紅：ΔE00／方向 | 眼影：ΔE00／方向 |
|---|---|---|
| 假鏡頭臉（4 款妝容） | 1.6–2.5／**1.00** | 0.7–1.0／0.76–0.94 |
| 真人臉（4 款妝容） | 0.8–1.2／**1.00** | 0.6–0.8／0.72–0.89 |

腮紅完全朝商品色走。**眼影偏淡**，但原因不在顏色模型：妝容本身設定的眼影濃度不高、再乘上覆蓋率 0.62；
而且眼影的漸層是從**眼球中心**往眉骨淡出，不是從睫毛根部 —— 到了眼皮上已經打了折。表上看到的「明度方向相反」
大多是量法的問題：眼皮在眼窩的陰影裡，拿去跟「沒有陰影的色卡」比，方向本來就會反。

沒有為了「看起來明顯」把眼影加濃 —— 這一輪的目標是忠於實品，沒有實拍對照就調濃只是換一種失真。
要改善，應該先拿實品眼影在真人眼皮上實拍，再決定是調覆蓋率、還是把漸層起點改到睫毛根部。

## 補做：把「還沒解決的」逐項處理

上一節末尾列了五項未解決。這一輪逐項做了四項，一項仍卡在沒有資料。

### 1. 眼白不可信時不再「完全不補償」

原本眼白取樣不可信就退回增益 1。**這是有實害的**：渲染器會把妝畫成「完全受光」的亮度，
暗場景下妝會比臉還亮。

新增 `estimateHighlight()`：改用臉上最亮的 2% 當光源參考。皮膚高光是菲涅耳反射，
幾乎不帶皮膚本身的顏色，所以接近光源色。準度比眼白差（仍混了一點皮膚的色，也會被粉底與出油影響），
但比不補償好得多。優先序是**眼白 → 高光 → 不補償**。

膚色判定仍然只認眼白：它的門檻是用眼白校準的，換來源會讓整批判定位移。
另外把**渲染用**的曝光夾限從 0.6–1.8 放寬到 0.25–6.0 —— 窄夾限是為了保護膚色判定，
暗場景下渲染會夾到頂。

量測台新增「曝光不變性」：把同一張臉調暗到 60%，渲染後除回曝光倍率，與全亮時的唇色比較。

| 暗場景的光源估計 | 與全亮時的唇色 ΔE00 |
|---|---|
| 眼白 | **5.7** |
| 高光退路（新增） | **12.0** |
| 不補償（原本） | **24.1** |

**還沒查清楚的**：放寬夾限前後幾乎沒有改善（5.8 → 5.7），所以殘差不是夾限造成的。
暗圖上眼白估出的增益比理論值（1 ÷ 0.6）高約 1.5 倍 —— 可能是 `estimateIlluminant` 的
取樣門檻（`mx < 60` 與「取最亮的四成」）在暗圖上篩出了不同的像素集合。這一項還沒解決。

### 2. 眼影偏淡：是量法不公平，不是沒上到

先前用「睫毛根部某一點應該等於覆蓋率混合色」判斷，結果差 ΔE00 20，看起來像沒上到。
**那個判準對眼影不成立** —— 眼影是漸層（由睫毛根部往上淡出）加羽化，不可能在任一點達到滿覆蓋率。

改成掃整條眼皮帶取峰值：峰值在眼皮往上 **38%** 處，色差 **2.4**，方向 **1.00**（完全朝商品色走）。
腮紅用同樣的滿濃度測法是色差 5.6、與預期混合只差 1.5。

所以眼影有正常上色，只是設計上就淡且擴散。要更明顯得動的是妝容的眼影濃度（0.30–0.45）
或漸層的淡出速度，那是美術決定，不是顏色模型的問題 —— 沒有實拍對照就調濃只是換一種失真。

### 3. 目錄色值 vs 商品照：一致

量測台新增這一節，逐支比對 `products.js` 的色值與商品照實際量到的顏色（`extractProductColor`）：

**12 支全部 ΔE00 ≤ 0.6。** 但要講清楚：商品照本身就是由色值參數化算圖產生的，
所以這是**一致性檢查，不是與實品的比對**。真正的驗證仍需實品拍照。

### 4. 2D 退路（沒有 WebGL 時）改用同一個顏色模型

`makeup.js` 原本是 `'color'` 混合：色相彩度換成商品、**明度留給底圖**。明度留的是嘴唇自己的（偏暗），
跟舊 WebGL 版同一個病。

現在先把底圖亮度乘上 `k = 商品亮度 ÷ 這個區域的平均亮度`，再做 `'color'` 混合 ——
`'color'` 保留背景明度，所以結果的明度正好是「商品亮度 × 原本的明暗起伏」。覆蓋率改成「混回原本的臉」，
霧面那層 `multiply` 拿掉（它是舊模型為了補強 `'color'` 才加的）。覆蓋率表與 WebGL 版共用 `COVERAGE`。

平均亮度只算**遮罩內**的像素 —— 用邊界框平均會被旁邊的皮膚拉高，唇會被畫得太暗。
每個區域各自快取 6 幀，臉的亮度不會逐幀劇變。

`_ar.html` 測試台 **12 項全部通過**（唇帶上色 ΔE 46.6、色相差 2.0°、明暗比例 1.084 → 1.071、
牙齒與區域外 ΔE 0.00）。效能 640×480：改寫前 0.87 ms → 未快取 4.35 ms → **快取後 1.56 ms**
（佔 30fps 預算約 5%）。

### 仍然卡住的一項：覆蓋率沒有用實拍校準

`COVERAGE` 仍是工程估計。要校準需要「實品塗在真人唇上、D65 光源、入鏡一張色卡」的照片，
這裡沒有這種資料。量測台已經備好接口：`?img=` 帶入照片後，「與預期混合色的差」那一欄就是擬合的目標函數。

## 情境推薦：心情、天氣、行程（第 2 步）

第 2 步的商品配方上方多了一排情境選項。選了之後，**質地、濃度與妝容建議**會跟著調整，
而且每一項調整都附上理由。

### 一條界線：量測 vs 你說的

膚色契合是**量出來的**（CIELAB / ITA° / 底調殘差）；心情、天氣、行程是**使用者自己說的**。
兩種證據的可信度差很多，所以：

- 情境**不寫進膚色契合分**，只在旁邊加權（`rankWithContext` 保留原本的 `score`，另外記 `ctxBonus`）
- 商品仍由 `resolveLook` 依量到的底調挑選，情境只覆蓋「偏好的質地」
- 畫面上兩種理由分開標示，面板下方直接寫：「情境是你告訴我們的，不是量出來的」

**沒選的項目完全不影響。** 三項都沒選時，質地、濃度、排序與原本逐項相同 —— 不說話的人不該被系統自作主張。

### 三項資料怎麼來

| | 來源 | 說明 |
|---|---|---|
| 心情 | 臉部模型的 52 個表情係數（`outputFaceBlendshapes`）| 拍照時猜一個**預設值**，使用者可以改。標示「表情自動判讀，可以改」|
| 天氣 | 使用者或櫃姐選；可由機台餵入 | **不連外網**。離線保證不能為了這個功能破掉 |
| 行程 | 使用者選 | — |

天氣的外部掛勾：`globalThis.__LUCID_WEATHER__ = 'hot' | 'humid' | 'mild' | 'cold'`，或網址 `?weather=hot`。
機台端（櫃位系統）可以定時寫入當地天氣，App 本身仍然不發任何對外請求。只接受認得的代碼，其餘忽略。

**表情不等於心情。** 沒在笑不代表心情不好 —— 所以那是預設值不是判決，一鍵就能改掉或取消。

### 規則（`js/context.js`）

規則全部寫死在一個檔案裡，每條都附理由 key。這些是化妝的一般常識，**不是量測結論**，畫面上照實說。

| 情境 | 質地 | 濃度 | 妝容加權 |

### 已知限制

- **表情判讀很弱**：規則是四條門檻（微笑 / 眉心上揚 / 眼皮沉重），不是情緒模型。它只負責給預設值。
- **規則是常識，不是量測**：沒有「這個天氣配這個質地」的實測資料支撐。要驗證需要真實的脫妝／持妝追蹤。
- **天氣需要人工或機台餵**：離線是刻意的取捨。
- 情境**永遠不會**改變膚色契合的判定 —— 這是設計，不是待辦。

## 主軸一：AI 的推薦與正面回饋

> 這一節描述的是第一版（單向的句子）。現在已改成**對話式**：AI 說完就給選項，點了就執行、再回話。
> 見〈改成對話：建議之後給選項〉。下面的規則（有依據才說話）在對話版完全沿用。

原本 AI 只在最後講一次話，而且是分析語氣（「契合度 71 大致契合」）。這一輪加了一層**顧問**：
把已經量到的數字翻成句子，在四個時機主動開口，並在最後給使用者**有依據的正面回饋**。

### 三條規則（`js/advisor.js`）

1. **每一句話都掛在一個量到的數字上。** 沒有數字支撐的稱讚不輸出 ——
   「你今天真美」誰都會說，機器說了只會讓人懷疑其他數字也是編的。
2. **不評價長相。** 講的是「量到什麼」與「可以怎麼做」，不是「好不好看」。
   這跟〈打分打的是契合度，不是好不好看〉是同一個立場。
3. **達不到標準就不硬誇。** 條件不成立時改給可以照做的建議，而不是把門檻調鬆來湊一句好話。

每句話都標出依據的種類：**肯定 / 量測 / 建議 / 留意**。畫面上顧問的視覺跟「情境」（使用者自述）
刻意不一樣 —— 量出來的跟你說的，不該長得一樣。

### 四個開口的時機

| 時機 | 說什麼 | 實測（假鏡頭臉） |
|---|---|---|
| 膚色分析完 | 量到的 ITA°、明度，底調明確或接近中性 | 「量到你的膚色 ITA° 72.3、明度 L* 74」「底調偏冷色調很明確（殘差 17.1°），挑色號的方向很清楚」 |
| 選定妝容 | 這款跟膚色契合幾分、理由；第一名不是它就照實說 | 「這款跟你的膚色契合 90 分（膚色明度高，濃唇對比效果最明顯），是很穩的選擇」 |
| 看配方 / 自己換色號 | 幾件對上底調、庫存；換色號時說跟前一支差多少、跟底調的關係 | 「這支跟剛才那支差 ΔE 23.3」「它是暖色調，跟你的冷色調相反 —— 會更搶眼，想要的話沒問題」 |
| 完成體驗 | **正面回饋**：存在感、底調契合、配色角度、總分 | 「上妝後唇與膚的對比比素顏多了 ΔE 23.3 —— 輪廓因此更清楚」「唇與頰的色相只差 16°，整組看起來是同一套」 |

第 4 步的區塊順序因此是：**給你的回饋（AI → 你）→ 體驗回饋（你 → 我們）→ 體驗報告**。
先讓機器把它量到的好消息說完，再請使用者評價。

### 撐不起來的時候怎麼辦

這是最容易做假的地方，所以測試特別針對它。契合度 41、色相差 62°、存在感 −1.2 的情境下：

- **一句稱讚都不會出現**
- 改成照實說「數字上沒有特別突出 —— 這是可以調的」
- 並附上可以照做的下一步（色相差太大就建議換接近唇色的腮紅）

`node test.mjs` 第 14 組（15 項）驗的就是這件事：低分不准出現 praise、高分的每一句肯定都要帶著它引用的數字、
換到相反底調時給建議而不是稱讚、所有句子的形狀一致（`adv.*` 文案鍵 + 已知類別 + 參數）。

### 已知限制

- 句子是**規則生成**的，不是語言模型 —— 機台離線，也不該為了一句漂亮話把顧客的臉送上雲端。
- 句型固定，同一個人多次體驗會看到重複的講法。
- 顧問引用的數字全部來自這台機器自己的量測，準度就是前面各章記錄的準度。

## 改成對話：建議之後給選項

顧問原本是單向的 —— 講完一段就沒了。現在改成**對話**：AI 說完話就給幾顆可以點的選項，
點了就真的執行，然後接著回話。使用者說過的話也會留在對話裡。

**不做開放式輸入框。** 機台離線，也不該把顧客的臉或對話送上雲端；能做的動作就那幾個，
做不到的事不要用一個輸入框假裝做得到。所以選項全部是這台機器真的執行得了的動作。

| 畫面 | 選項 | 點下去會發生什麼 |
|---|---|---|
| 推薦（第 1 步） | 為什麼這樣判斷？／換成分數最高的那款／就這款，看商品 | 攤開底調的算式；換妝容並重算配方；先算配方再進第 2 步 |
| 配方（第 2 步） | 換成中性色／再淡一點／開始試妝 | 把跟底調相反的換成中性色；三個部位濃度 ×0.8；進 AR |
| **AR（第 3 步）** | 更明顯一點／再淡一點／換下一個色號／跟素顏比一比／兩支一起比／放大看看 | 濃度 ×1.2 或 ×0.8；換下一支有貨的唇色；切素顏對比；切雙色對比；開唇部放大 |
| 回饋（第 4 步） | 這分數怎麼算的？／再試別的妝容 | 攤開加權算式；回到妝容推薦 |

「為什麼」不是換句話再說一次結論，是**把算式攤開**：

> 明度 L* 74 對應的中性色相基準是 65°，你量到的是 48° —— 差 −17.1° 就是底調的判定依據。
>
> 契合度 = 膚色 75 分 ×0.40 + 配色（唇頰色相差 30°）×0.32 + 強度（上妝幅度 ΔE 2.7）×0.28，合起來 59 分。

「為什麼」回傳的是算式而不是結論、沒有資料時不亂編。

### 對話會「鬼打牆」的四個來源，以及怎麼堵住

改成對話之後出現一個現象：連點同一顆選項，畫面會疊成一排一模一樣的話，
看起來像機器卡住了。拆開來是四件不同的事，各自要用不同的方法處理 ——
「把重複的字串濾掉」只解決得了其中一件。

| 來源 | 原本的樣子 | 處理 |
|---|---|---|
| 同一句話連講兩次 | 換妝容時膚色那兩句整段重建、重新出現 | `chatSay` 比對前一句 AI 的 `key+params`，一樣就不講；換妝容改成「接著講」而不是重建 |
| 狀態句越疊越多 | 每調一次濃度就多一句「現在是 …」 | `chatReplace`：同一類的舊狀態句先移除再講新的 |
| 點了等於沒動 | 濃度到頂還留著「更明顯一點」，點下去數字不動、話也一樣 | 濃度上下限 `AMOUNT_MIN/MAX` 由 `advisor.js` 統一發，`dropDeadAmount` 把到極限的那一顆收掉；問過的「為什麼」由 `dropAsked` 收掉 |
| 開關只有開、沒有關 | 「跟素顏比一比」按第二次狀態沒變，只剩一顆沒人回的「你：…」 | 對比模式改成真開關（`opt.compareOff` / `opt.dualOff`），標籤說得出「再按一次會怎樣」；畫面上的模式鈕與放大鈕改狀態時，用 `syncAROpts()` 把對話裡的標籤同步過去 |

還有一個只有在畫面上才看得出來的殘留：狀態句被換掉之後，它前面那顆「你：…」就成了
**沒有人回應的孤兒**，連按幾次就疊成一排。`chatReplace` 因此多一條規則 ——
後面已經沒有 AI 回應的使用者氣泡，只留最後一句。

驗收（假鏡頭臉，`_camtest.html`）：

| 操作 | 結果 |
|---|---|
| 連點 5 次「再淡一點」 | 濃度停在 15，選項自動收掉，對話只留 1 句「你：再淡一點」＋現況 |
| 連點 8 次「更明顯一點」 | 濃度停在 100，同上 |
| 連點 4 次妝容卡片 | 膚色那兩句不重複，評語被換掉而不是疊上去 |
| 亂點 24 次（9 種動作輪流） | 對話總共 6 則，連續的「你：…」最多 **1** 句 |
| 對比／放大按到第二次 | 真的關得掉，回「收起素顏對比，回到整臉的妝」 |
| 「為什麼」問第二次 | 選項已經不在了（同一題問第二次沒有新資訊） |

`node test.mjs` 第 16 組把這幾條規則固定住：極限值收選項、問過就不再問、
對比開關的標籤跟著狀態走、兩個開關互不影響。

### 讓互動變雙向：AI 會問、會記、會主動開口

到上一節為止，對話仍然是單向的：使用者下指令，AI 回應。這一輪補上另外三個方向 ——
**AI 反問**、**記得你做過什麼**、**不用等你點也會開口**，最後在回饋畫面把整場引用回來。

四件事都守著同一條線：每一句話仍然掛著一個量到的數字，而且**問了就要做得到**。

#### 1. AI 反問（`askAmount` / `observe`）

只問「答案會真的改變接下來做什麼」的問題。問完沒有後續的問題不要問 ——
那只是把對話拉長，不是互動。

| 時機 | 問句 | 答案的實際效果 |
|---|---|---|
| 第 2 步進來 | 「現在三個部位的濃度都是 92。今天想低調一點，還是明顯一點？」 | 低調 → ×0.7（92→64）；明顯 → ×1.3；兩者都記進偏好 |
| AR 閒著 12 秒且試過 ≥3 支 | 「你試過 3 支。其中 #307 的色卡跟你的膚色差最多（ΔE 63.6）—— 要換回那一支看看嗎？」 | 真的換過去，並報出 ΔE |

問句用「請問」標籤與較重的字重標出來，下面那排就是答案。
**但原本能做的事全部留著** —— 被 AI 問一句就什麼都不能做，那是把對話變成關卡。

#### 2. 記得你做過什麼（`js/advisor.js` 的偏好層）

不做問卷，只認兩種行為證據：

- **自己按了「再淡／更明顯」** —— 差兩次以上才算偏好（一來一回不代表什麼）。
- **在某支色號上真的停了下來** —— 6 秒為界。比這短的多半只是滑過去，算進偏好就是在編故事。

停留過的色號裡，同一個底調要**至少兩支且明顯多於其他**才算數；冷暖各兩支就是打平，打平不下結論。

偏好一旦成立，三個地方會用到它，而且每次都說得出依據：

| 用到的地方 | 畫面上的樣子 |
|---|---|
| AR 換下一個色號 | 優先給同底調，並說「你在 2 支暖色調上都停留超過 6 秒 —— 這支也是暖色調，所以先給你這支」 |
| 回到配方畫面 | 「上一輪你在 2 支暖色調上都停留超過 6 秒 —— 要把唇色換成暖色調的嗎？」＋一顆「換成我停留過的那種」 |
| 點下去之後 | 「唇色換成 #512 蜜桃汽水（暖色調）—— 你在這一支上停了 8 秒」 |

唇色**本來就已經是**那個底調時，這句話不會出現 —— 問一句沒有答案的問題比不問更怪。

#### 3. 主動開口（`observe`）

不等使用者點。但主動說話很容易變成吵人，所以寧可少講：**一種情況一場只講一次**，
使用者一動作就重新計時，而且第一個成立的才講，不會一次倒三句。

| 條件 | 說什麼 |
|---|---|
| 唇寬 < 畫面寬的 9% | 「你離鏡頭有點遠，唇部只佔畫面寬的 6.4% —— 靠近一點，或用放大檢視會看得比較準」 |
| 閒著 12 秒 + 試過 ≥3 支 | 反問「要不要換回對比最大的那一支」（見上表） |
| 閒著 20 秒 | 「這支的色卡跟你的膚色差 ΔE 63.6。想比較的話，可以換一支，或開素顏對比看差別」 |

假鏡頭臉實測唇寬佔 12.1%，不會誤觸「離太遠」。

#### 4. 收尾引用整場（`sessionSummary`）

第 4 步的回饋不再只講這一次的分數，還把這一場真的發生過的事講回去 —— 全部是數字，
沒發生的就一句都不講（只試一支、濃度沒動、沒有偏好 → 這一段完全不出現）：

> 量測　你今天試了 3 支唇色，最後停在 #204 蜜楓棕。
> 量測　濃度從 92 調到 64 —— 這是你自己調的，不是預設值。
> 量測　你停留超過 6 秒的色號有 2 支是暖色調 —— 回到配方畫面時可以一鍵換成這個方向。

#### 5. 心情、天氣、行程改成 AI 來問

這三項原本是畫面上的一排按鈕，使用者得自己想到要去點。現在由 AI 在配方畫面**依序問**，
問完才問濃度 —— 情境會改變挑出來的商品，先問才有意義。

| 題 | 問法 | 答完會發生什麼 |
|---|---|---|
| 心情 | 表情猜得到時：「從你剛才的表情看起來像是「緊張」—— 是這樣嗎？（猜的，你說了才算）」 | 重挑商品與濃度，並回「記下了。緊張 —— 走最不會出錯的自然感」 |
| 天氣 | 有氣象來源時同樣先確認，沒有就直接問 | 「乾冷唇容易裂 —— 改用水光、腮紅補氣色」，唇彩真的換成水光質地 |
| 行程 | 「等一下要去哪裡？行程會影響妝的濃淡跟質地。」 | 「約會 —— 唇改水光、腮紅加一點」 |

每一題都有「不想說」：跳過的項目完全不影響推薦，AI 也照實這樣說。

兩個刻意的選擇：

- **猜到了也要問。** 表情猜心情、氣象來源給天氣，原本是直接填進去當成事實用。
  現在改成「我猜是這個，對嗎」—— 猜了不講、直接當真，是這台機器最不該做的事。
- **答案標成「你說的」，不是「量測」。** 對話裡多了一種語氣標籤（`told`），
  跟量出來的那些分開。兩種證據的可信度不一樣；混成同一種語氣講，
  量出來的那些也會跟著貶值。這跟〈情境推薦〉那一節是同一個立場。

#### 6. 對話不會停在沒得點的地方

實際踩到的當機：在推薦畫面還沒選妝容時點「為什麼這樣判斷？」，問過的題目會被收掉，
而那時候**只有這一個選項** —— 收掉之後整段對話就沒有任何東西可以點了。

修法是三層，最後一層是保險：

1. 還沒選妝容時，選項裡一定有一條往前的路（「就從第一名開始」）。
2. 動作沒帶新選項回來時（例如沒東西可換回、沒有相機），把原本那排放回去 ——
   `chatYou` 會先清空選項，不還回去對話就停在那裡了。
3. `mountChat` 過濾完如果一個都不剩，退回這個畫面的預設選項。

另外，沒有相機的機台（上傳照片的流程）點「開始試妝」原本是**靜靜地什麼都不做** ——
沉默看起來就是壞掉。現在會照實說：AR 需要即時畫面，但上傳照片的流程仍然看得到合成與回饋。

驗收：從推薦畫面開始亂點 **77 次**（每次隨機挑一顆，跨越第 1–4 步），
沒有任何一個畫面出現過「沒有選項」的狀態。

#### 7. 「為什麼」可以一路追問下去

「為什麼這樣判斷？」原本答完就結束，選項只剩一個 —— 一個肯回答的顧問，
**被追問第二次還答得出來**才算數。所以解釋之後接著給三個追問，而且追問一樣只攤開量到的數字。

膚色那一邊（第 1 步）：

| 追問 | 回答（假鏡頭臉實測） |
|---|---|
| 深淺是怎麼分的？ | 「ITA°（明度與黃藍軸的夾角）：你量到 72.3°，落在 >55° 這一帶 = 極淺。ITA° 只管深淺，冷暖是另一條線算的 —— 所以深膚色一樣可以是冷調。」 |
| 光線有影響嗎？ | 「取到 762 點眼白，估到色溫約 5709K，把畫面換算回 D65 之後才判定 —— 不補償的話櫃位的暖光會把膚色整片推成暖調。」眼白量不到時改講「這次只有 N 點，判定會比平常不穩」，並標成「留意」 |
| 這跟推薦有什麼關係？ | 「櫃上有貨的唇色有 5 支，其中 3 支是冷色調或中性 —— 推薦只會從那 3 支裡挑。」 |

分數那一邊（第 4 步）：

| 追問 | 回答 |
|---|---|
| 色相差是什麼？ | 「配色分 = 100 − 1.7 × 唇頰色相差。你這組差 16°，所以是 73 分；18° 以內看起來像同一套配色。」 |
| 上妝幅度怎麼算？ | 「素唇到上妝後的 ΔE：量到 28.3。這款妝容的期望值是 19.6，差 8.6 —— 完成度 74 分。」 |
| 跟素顏差多少？ | 「存在感 = 上妝後的唇膚對比 − 素顏的唇膚對比 = ΔE 26.2，落在『有明確的妝感』這一級。這是比素顏多出來的部分，不是唇色本身有多深。」 |

追問跟「為什麼」一樣是一次性的：問過就從選項收掉（同一題問第二次沒有新資訊），
但**往前的那條路永遠留著**。沒有資料時一律不回答 —— 六個追問全部在沒有量到東西時回空，不亂編。

`node test.mjs` 第 19 組（11 項）鎖住這一段，包含「眼白量不到要標成留意」與「沒資料不亂編」。

`node test.mjs` 第 17 組（27 項）鎖住這一整層：反問要掛數字、答案要對得上真的動作、
5.999 秒不算停留、同一支停兩次只記一次、打平不下結論、依偏好挑色號時要說得出依據、
講過的不再講、只試 2 支不問「哪支對比最大」、以及「沒發生的事不寫進收尾」。
第 18 組（15 項）鎖住上面這兩件：任何畫面都留得下一步、一次性的答案答完就收掉、
猜到的心情要改成「確認」而不是當成事實、情境的回答一律標成「你說的」。

### 互動方式：除了點選項，還能點臉、看圈選、點頭

對話到這裡仍然只有一種互動方式：在下面那排選項裡點一顆。
這一輪補上三種真的用到「鏡子」這個介面的方式。

#### 點鏡子裡的臉，就是在問那個部位

鏡面上輕點（短按、幾乎沒移動）＝ 問那個部位；**按住仍然是看素顏、拖曳仍然是移動分界線**，
三種手勢互不干擾。判定半徑跟著臉寬縮放，所以人靠近或走遠都一樣準。

| 點的位置 | AI 的回答（假鏡頭臉實測） | 同時發生的事 |
|---|---|---|
| 唇 | 「唇上現在是 #307 冷調正紅，濃度 92，色卡跟你的膚色差 ΔE 63.6」 | 下面的細調切到「唇彩」 |
| 眼周 | 「眼周現在是 四色眼影盤（冷色調），濃度 35」 | 切到「眼影」 |
| 頰 | 「頰上現在是 空氣感腮紅（冷色調），濃度 30」 | 切到「腮紅」 |
| 臉（額、鼻樑一帶） | 「圈起來的 10 塊就是量膚色的地方：ITA° 72.3、明度 L* 74、底調冷色調」 | 鏡面圈出那 10 塊，並給膚色的三個追問 |

#### AI 把講到的數字圈回臉上

講「取到 762 點眼白」的時候，鏡子上就把那兩塊圈起來。數字留在文字裡、臉上什麼都不標，
使用者只能選擇相信；**圈出來才查得證**。

| 講到什麼 | 圈哪裡 |
|---|---|
| 底調／深淺怎麼判的 | `sampleSkin` 真正量的那 10 塊皮膚 |
| 光線有影響嗎 | 兩眼的眼白輪廓（白平衡的取樣處） |
| 色相差是什麼 | 兩頰（腮紅色的來源） |
| 上妝幅度／跟素顏差多少 | 唇的外輪廓 |

圈選 0.2 秒淡入、2.6 秒後自己淡掉，不會擋著看妝。
驗收是量畫布像素：圈之前頰部那一圈只有 11/60 是白的，圈之後 59/60；同一時間眼周維持 0/60，
沒有畫到不該畫的地方；過期之後再畫一次，畫面完全不變。

#### 是非題可以點頭或搖頭

在鏡子前面，點頭比找一顆按鈕自然。但誤判的代價是「幫使用者做了他沒要的決定」，所以：

- **只在有是非題等著回答的時候才啟用**，其他時候完全不看臉部動作。
- 判定要同時滿足三件事：幅度 ≥ 臉寬的 5.5%、方向來回至少兩次、而且另一軸明顯比較小。
  只看幅度會把「低頭看商品」當成點頭；只看次數會把輕微晃動當成搖頭。
- **認出來之後先講出來**：「偵測到點頭 —— 當成『好』。不是的話下面的按鈕隨時可以改。」
  按鈕從頭到尾都在，手勢是多一條路，不是取代。

為了讓這條路真的用得到，AR 多了一題會重複出現的是非題：在同一支色號上停留超過 10 秒又沒有動作時，
AI 會問「你在 #307 冷調正紅 上停了 10 秒 —— 要把它留下來嗎？」（每支只問一次）。
答「留這支」會記進偏好（收尾會講），答「再看別支」就直接換下一支。

實測（注入合成的鼻尖軌跡）：點頭 → 執行「留這支」，回「#307 留下了 —— 目前留了 1 支」；
搖頭 → 執行「再看別支」，色號真的從 #512 換成 #455。

`node test.mjs` 第 20 組（18 項）鎖住這三件：點在很遠的地方不亂猜、沒有臉不會炸、
慢慢低頭不算點頭、幅度太小不算、畫圈（兩軸差不多）就不猜、同一支只問一次、還在操作就不插話。

## 第 2 步改成「臉型 + 白話」的推薦

原本第 2 步的說法是「量到你的膚色 ITA° 72.3、明度 L* 74」「底調殘差 17.1°」——
對來櫃上試妝的客人來說太像實驗報告。這一輪改兩件事：

1. **主要說辭改成客人聽得懂的話**，像櫃上的彩妝師在講：「膚色是白皙、偏冷調（帶一點粉）——
   粉紅、玫瑰、莓果這類顏色上臉會很乾淨」。數字沒有刪掉，收進「臉型是怎麼看的？」「膚色是怎麼看的？」
   這些追問裡 —— 依據還在、隨時問得到，只是不擋在前面。
2. **加入臉型分析，並讓臉型真的影響推薦**：因為是什麼臉型，所以哪一款妝容適合，再附上同樣臉型的明星例子。

### 實際畫面（假鏡頭測試臉）

> 量測　你的臉型介於鵝蛋臉和長臉之間，兩種的畫法都很適合你。
> 量測　膚色是白皙、偏冷調（帶一點粉）—— 粉紅、玫瑰、莓果這類顏色上臉會很乾淨。
> 建議　腮紅小技巧（鵝蛋臉）：從蘋果肌往太陽穴斜斜刷開，自然的立體感就出來了。
> 肯定　推薦「自然偽素顏」：鵝蛋臉比例均衡，薄透的妝最能讓你本來的輪廓說話。顏色也跟你偏冷的膚色很搭。
> 參考　同樣是鵝蛋臉、美妝雜誌常拿來當例子的有碧昂絲、潔西卡·艾芭，可以參考她們的妝容找靈感。

妝容卡片也不再顯示百分比：第一名標「最推薦」，說明優先寫「很襯鵝蛋臉」；
沒有臉型理由的卡片，膚色理由也改成白話（「皮膚白皙，濃一點的唇色會特別亮眼」）。

點「臉型是怎麼看的？」時，照片上會畫出量的線（臉長、額頭寬、臉寬、下顎寬），AI 講數字：

> 照片上的線就是量的地方：臉長大約是臉寬的 1.58 倍，額頭寬是臉寬的 96%，下顎寬是 77%，下巴線條圓順。
> 鵝蛋臉的典型比例是臉長約 1.3–1.5 倍臉寬、顴骨最寬。

### 怎麼量（`js/faceshape.js`）

依一般臉型量測指南量四個尺寸，再加兩個線條特徵：

| 特徵 | 怎麼量 |
|---|---|
| 臉長 ÷ 臉寬 | 髮際線到下巴 ÷ 顴骨寬（MediaPipe 234↔454） |
| 額頭寬 ÷ 臉寬 | 太陽穴（21↔251） |
| 下顎寬 ÷ 臉寬 | 下顎角（172↔397） |
| 下巴收窄 | 下巴兩側（149↔378）÷ 下顎寬 |
| 下顎轉角 | 下顎角 → 顴骨、下顎角 → 下巴兩條線的夾角 |

**髮際線要在照片上找。** MediaPipe 最上方的點在額頭中段，不是髮際線；用五官比例（三庭）推算，
測試臉會量成 1.72 倍，實際是 1.58 倍。所以沿著臉的中線往上走，找膚色變成頭髮的地方。

- 只走正中間的話，**中分髮型**會沿著頭皮分線一路往上走（測試臉就是這樣，量成 1.63）。
  改成走三條線（正中與左右各偏臉寬 12%），取中位數。
- 瀏海、淺色髮讓它找不到時，改用比例估，並照實說「髮際線看不清楚，臉型只能當大概的參考」；
  照片上的髮際點也會變成黃色。
- 驗收：在照片上把量測線畫出來、完整顯示整張照片目視確認 —— 髮際點落在額頭頂端的髮際線上。
  也因為畫出來才發現，我最早「目測 1.42 倍」是看錯的，連帶估計係數從 0.55 更正為實測的 1.25。

分類用六種臉型的典型值算相似度：長寬比的範圍取自公開的比例表（鵝蛋 1.30–1.50、圓 1.00–1.25、
方 1.00–1.28、長 1.50 以上、心形 1.25–1.55、菱形 1.35–1.55），其他四項依表上的描述訂。
第一名與第二名差距小於 0.15 時講「介於兩者之間」；六種都不像（側臉、遮擋）時不給結論，只用膚色推薦。

### 臉型怎麼影響推薦

| 臉型 | 常見建議 | 加分的妝容 |
|---|---|---|
| 鵝蛋臉 | 比例均衡，打亮顴骨帶出立體感 | 韓系微光、自然偽素顏 |
| 圓臉 | 腮紅往太陽穴斜刷、霧面增加輪廓 | 清透通勤、復古氣質 |
| 方形臉 | 圓弧暈染、柔光讓線條柔和 | 韓系微光、自然偽素顏 |
| 心形臉 | 用唇色平衡下半臉 | 韓系微光、復古氣質 |
| 長臉 | 腮紅橫刷在蘋果肌 | 自然偽素顏、韓系微光 |
| 菱形臉 | 顏色放蘋果肌、不堆在顴骨 | 清透通勤、自然偽素顏 |

加分乘上分類的把握度，「介於兩者之間」時兩邊都加一點。
**第一版只加 4–6 分，結果臉型講得再清楚，第一名仍然完全由膚色決定**（測試臉照樣推復古妝）——
等於只是在說明，沒有在推薦。現在拉到 12–18 分，跟四款妝容膚色分數之間的差距同一個量級，
測試臉的第一名因此變成「自然偽素顏」，理由是臉型。膚色分數與臉型加分仍分開記，不混成一個數字。

### 三個要先講清楚的限制

1. **臉型分類本身就不精確，而且原始前提跟這台機器的立場衝突。**
   臉型比例表起源於 1930 年代好萊塢化妝師 Westmore 兄弟，前提是「鵝蛋臉最理想，其他臉型用妝修成鵝蛋臉」。
   這裡不採用那個前提：只講「怎麼畫會襯出這個臉型本來的樣子」，**文案裡不出現修飾、顯瘦、小臉、缺點**
   （測試會掃過全部臉型文案檢查）。
2. **門檻沒有用標註過臉型的真人照片校準。** 手上只有一張看得到髮際線的測試臉。
   要讓臉型判斷可以正式上線，需要一批由彩妝師標註過臉型的照片（建議至少 30–50 張、涵蓋各臉型）來調典型值。
3. **明星臉型在不同媒體常互相矛盾。** 一份 2019 年的研究整理已發表資料，117 位女星裡有 62 位被分到不同臉型
   （例如 Keira Knightley 有人列方臉、有人列長臉；Rihanna 有人列鵝蛋臉、有人列菱形臉）。
   所以只收三份清單裡**至少兩份分到同一類、而且沒有被列在其他臉型**的人，
   只當「這種臉型的例子」、不說使用者像誰，只放名字不放照片。
   商業場合若有肖像或代言上的顧慮，把 `SHOW_CELEBS` 設成 `false` 就整句不出現。
   目前查到的清單以歐美明星為主，**亞洲明星沒有找到多來源一致的資料**，所以暫時沒有收；
   若要放台日韓明星，建議由店方提供並確認過的名單。

## 拍照「按了沒反應」

手機回報：倒數完什麼事都沒發生。截圖裡倒數到 1 時，鏡頭只拍到天花板和頭頂。三層原因：

1. **失敗訊息被立刻蓋掉。** 分析發現沒有臉時會顯示「偵測不到臉」，但取景提示每 0.25 秒更新一次，
   馬上又把它換回「請將臉部對準框內」—— 使用者看到的就是「按了沒反應」。
   現在失敗訊息會停留 3.5 秒（錯誤 6 秒），框線閃一下，文字也改成告訴人該怎麼做：
   「沒有拍到完整的臉 —— 請把整張臉放進框內，再按一次拍照」。
2. **分析出錯會靜靜停住。** 拍照與上傳照片都沒有錯誤處理，出錯就沒有下文。
   現在會顯示「分析時發生錯誤，請再拍一次；如果一直失敗，可以改用上傳照片」。
3. **倒數中可以重複按。** 每按一次就多一個倒數、多拍一張。現在倒數期間按鈕停用，結束（成功或失敗）後才恢復。

驗收：把鏡頭換成一個沒有臉的畫面，連按兩次拍照 —— 只跑一個倒數、倒數期間按鈕停用、
結束後出現上面那句提示且框線閃爍、按鈕恢復可按、停在第 1 步。

## Galaxy S25 上仍然無法拍照：偵測自我檢查與 CPU 退路

修好「失敗訊息被蓋掉」之後，S25 上臉在框內仍然拍不了。沒有實機可以重現，
最可能的原因是 **MediaPipe 的 GPU 模式在部分 Android 手機與瀏覽器的組合上「不報錯、但永遠偵測不到臉」**
—— 鏡頭畫面正常，錯誤處理也抓不到任何東西。所以不靠猜，改成讓程式自己驗證：

1. **開機自我檢查**（`js/face.js` 的 `selfTest`）：用一張內建、確定有臉的小圖（264×316，14 KB，`js/selftest-face.js`）
   跑一次偵測。GPU 建立失敗或自我檢查沒過，就關掉 GPU 偵測器、改用 CPU 重建並再檢查一次。
2. **取景偵測先把影片畫到 640px 寬的小畫布**再偵測，避開部分 Android GPU 直接讀 `<video>` 畫面的問題，手機上也比較快。
3. **連續兩次偵測不到臉，就把診斷資訊附在提示後面**：
   「（診斷：CPU／自檢 OK／鏡頭 1280×960／照片 720×540）」。臉明明在框內還是失敗時，截這一行就能遠端判斷。
4. **現場排查用的網址參數**：`?cpu` 直接用 CPU；`?gpufail` 模擬 GPU 自我檢查失敗（用來驗證自動切換）。

驗收（假鏡頭臉）：

| 模式 | 自我檢查 | 拍照 → 第 2 步 | AR 追蹤 |
|---|---|---|---|
| 預設（GPU） | 通過 | 正常 | 正常 |
| `?cpu` | 通過 | 正常 | 57 fps、每幀 22.5 ms |
| `?gpufail`（GPU 失敗 → 自動換 CPU） | 通過 | 正常 | 正常，沒有任何 JS 錯誤 |

單檔版也重新確認可以開機。**這一段沒有在 S25 實機上驗證過** —— 如果實機上仍然失敗，
需要那一行診斷資訊，才能分辨是偵測模式、鏡頭解析度還是瀏覽器本身的問題。

## AI 對話改成訊息氣泡

所有顧問對話（推薦、商品、AR 抽屜、回饋）統一成聊天 App 的樣子：

- **AI 頭像＋左側白色氣泡**；連續幾則 AI 訊息只在第一則放頭像，看起來像同一口氣講完的話。
- **自己的選擇是右側玫瑰色氣泡**。
- **快速回覆是下方的膠囊按鈕**。
- AI 的提問氣泡有玫瑰色外框，「参考」（明星例子）的氣泡是半透明 —— 性質不同的話，看得出不同。

**對話的節奏**：AI 回覆前先顯示「輸入中」的三個點，再一句一句出現（第一句 0.42 秒、之後每句 0.38 秒），
新訊息滑入。一次倒出一整段比較像公告，不像對話。**快速回覆等 AI 講完才出現** ——
話還沒說完就先給選項，順序就亂了。節奏刻意短，是為了讀得出一來一回，不是為了拖時間；
系統設定「減少動態效果」或網址帶 `?fast` 時全部立刻顯示。

實作上每則 AI 訊息帶一個 `revealAt`，`mountChat` 只畫已經到時間的，還沒輪到的換成「輸入中」氣泡並排好下一次重畫。
延遲只影響「顯示」，不影響動作 —— 點「再淡一點」時濃度是立刻變的，只有 AI 的那句話晚半秒出現。

驗收：第 2 步開場三句依序出現、期間有輸入中、快速回覆最後才出現；點選項後先出現自己的氣泡與輸入中，
約 0.5 秒後才回覆。延遲出現之後重跑全流程隨機點選（第 2～5 步共 23 次，每次等 AI 講完再點），
沒有卡在沒選項的狀態、沒有 JS 錯誤。

## 對話再精簡、加上表情符號

- **表情符號**（`js/emoji.js`）：只在顯示時加在句子與快速回覆前面，**不寫進三種語言的文案**。
  臉型 ✨、膚色 🌸、腮紅 🍑、推薦妝容 💄、明星例子 🌟、AI 提問 💬、建議 💡、留意 🙏；
  快速回覆如 更明顯 💥、再淡一點 🌿、換色號 🎨、跟素顏比 👀；心情／天氣／行程的答案各有自己的符號（😊 ☀️ 💕…）。
  按下去之後，右側「你」的氣泡帶著同一個符號，一問一答對得起來。
- **不用在評價長相的符號**：沒有 😍🥰😘👑🔥💋；留意類的句子用 🙏 而不是嚇人的 ⚠️（測試會掃對照表）。
- **開場打招呼**：推薦畫面先說「嗨～照片看好了，跟你說說我看到什麼」，回饋畫面先說「辛苦了～這是今天試妝的結果」。
- **精簡**：拿掉「AI 顧問」標題（頭像就代表是 AI）；氣泡、頭像、快速回覆與間距都縮小。
- **種類標籤只留「你說的」**：句首符號已經看得出是建議、提問還是例子，標籤每句都掛只是重複；
  「你說的」保留，因為那句話的依據是客人自己的回答、不是量測，這個差別要一直看得到。

`node test.mjs` 第 22 組（7 項）：31 種快速回覆都有符號、情境答案各有自己的符號、抽查的每句話都配得到符號、
對照表裡沒有評價長相或嚇人的符號。

## 對話區固定高度、往上捲

對話越講越長，會把推薦卡片、商品清單往下擠。訊息區改成固定高度（桌機 176px、手機 148px、回饋頁 210px），
**新訊息出現在底部、舊的往上捲出去**，往上滑就看得到歷史（最多保留 24 則）；捲離頂端時上緣淡出，提示上面還有訊息。

捲動的兩個規則：
- **AI 講了新的話（或出現「輸入中」）→ 自動捲到最新。**
- **使用者正在往上翻舊訊息、又沒有新訊息 → 留在原位。** 對話常因為選項標籤更新而重畫，
  不處理的話，每次重畫都會把人拉回底部，舊訊息根本看不完。

驗收：第 2 步連問四題之後，整個對話框維持 263px，裡面 577px 的訊息自己捲動並停在最新一則；
AR 抽屜裡往上翻到最頂、再用畫面上的模式鈕觸發重畫，位置仍停在最頂；接著點一個會回話的選項，就捲到最新。

## 不只推薦給女性：男士妝容

原本四款妝容都是女性取向（正紅唇、珠光眼影…），明星例子也全是女星。

**用問的，不從臉去猜。** 從臉部判斷性別很容易錯，猜錯也很冒犯人；想試哪種妝本來就是個人選擇。
推薦畫面講完臉型與膚色後，AI 問一句：

> 💬 想看哪一類的妝容？男生也可以試試看，清爽的男士妝容看不太出上妝喔
> 〔💄 女性妝容〕〔🧴 男性妝容〕〔🙌 都可以〕

不回答就當「都可以」，排序完全不動。

**新增「清爽男士妝」**（`js/products.js`）：看不出上妝的清爽感，三個部位濃度都壓在 0.25 以下，
而且**不管哪種膚色都先挑中性色**（`neutralFirst`）—— 照一般規則，冷調膚色會被配到正紅唇與玫瑰灰粉，
對「看不出上妝」來說太明顯。實際配到：#118 玫瑰豆沙、03 香檳裸金、03 裸粉。

**選了之後會變的東西：**

## AI 自動判斷先排哪一類妝容

使用者要求加入自動判斷。上一版刻意「用問的，不從臉去猜」—— 從臉判斷性別會錯，猜錯也冒犯人。
所以這裡把判斷結果當成**預設值，不當結論**：

1. **沒把握就不猜**：模型把握度 ≥ 85% 才套用，不到就退回原本的問法。
2. **套用時照實說、一鍵能改**：
   > 💬 AI 先幫你排了女性妝容為主（依照片自動判斷，不一定準）—— 想換的話點下面
   > 〔👍 就這樣〕〔🧴 男性妝容〕〔🙌 都可以〕〔🤖 AI 怎麼判斷的？〕

   講的是「先排哪一類妝容」，不說「你是男性／女性」（測試會掃文案）。
   使用者親自選過之後，重拍也不再用 AI 猜的蓋掉。
3. **全部在這台機器上跑**：照片不上傳、結果不存檔，重新開始就清掉；點「AI 怎麼判斷的？」會照實講模型、把握度與門檻。
4. **只用性別輸出**：模型同時算出的年齡不使用、不保存。
5. **可以關掉**：`js/gender.js` 的 `AUTO_GENDER` 改成 `false`，或網址帶 `?nogender`（此時完全不會載入模型）。

**模型**：[@vladmandic/face-api](https://github.com/vladmandic/face-api) 1.7.15 的 AgeGenderNet（MIT，face-api.js 的維護分支），
由 `node vendor.mjs` 抓到 `vendor/face-api.js`（1.3 MB，內含 TensorFlow.js）與 `models/age_gender_model.*`（430 KB），
授權文字在 `vendor/face-api.LICENSE`。臉的裁切框直接用 MediaPipe 的關鍵點算（正方形、留 25% 邊），不另外載臉部偵測器。
單檔版的權重是 blob 網址，沒有資料夾可以相對讀取，所以用「權重清單＋二進位檔」自己解（`tf.io.decodeWeights`）。

**速度**：WebGL 第一次推論要先編譯著色器（實測 4–5 秒），之後每次約 20 ms（CPU 約 400 ms）。
第一版因此讓「按拍照到第 2 步」從 2.5 秒變成 7.3 秒。改成模型載入後在背景用空白圖暖機一次，
拍照時最多只等 1.2 秒、還沒暖好就不猜。現在按拍照到第 2 步 2.53 秒（其中 2.4 秒是倒數）。

**限制要先講清楚**：這類模型的訓練資料在人種、年齡上有已知偏差，對跨性別與非二元性別的人也不適用 ——
這正是它只能當預設值、不能當結論的原因。**目前只用一張測試臉驗證過**（判為女性、把握度 94%）；
上線前應該用涵蓋不同年齡、膚色的一批照片，量一次「套用率」（超過門檻的比例）與套用時的錯誤率。

驗收：開發版與單檔版都能載入模型並套用；選「男性妝容」後排序與小技巧改成男士版、確認選項消失；
`?nogender` 時改回用問的、而且沒有請求任何模型檔。`node test.mjs` 第 24 組（12 項）鎖住門檻、裁切框、確認問題的選項與文案。

## 心情、天氣、行程由 AI 在推薦畫面問

原本這三題在商品頁（第 3 步），而且畫面上還留著一整排情境按鈕 —— 看起來像填表單，不像 AI 在問；
而且這三項會改變推薦**哪一款妝容**，等到商品頁才問已經晚了。

現在推薦畫面（第 2 步）的對話依序問，一次一題，答完才問下一題：

> 💬 AI 先幫你排了女性妝容為主（依照片自動判斷，不一定準）… 〔👍 就這樣〕…
> 😊 從你剛才的表情看起來像是「緊張」—— 是這樣嗎？（猜的，你說了才算）〔👍 對，就是這個〕〔😊 有精神〕…〔🤐 不想說〕
> 🌤️ 外面的天氣呢？這會影響質地 —— 悶熱容易脫妝，乾冷唇容易裂。〔☀️ 悶熱〕〔🌧️ 潮濕〕〔🌤️ 舒適〕〔❄️ 乾冷〕…
> 📅 等一下要去哪裡？行程會影響妝的濃淡跟質地。〔💼 上班上課〕〔🎤 面試簡報〕〔💕 約會〕〔🥂 聚會晚宴〕〔🛍️ 隨意外出〕…
> 💄 好～綜合你的臉型、膚色和今天的狀態，最推薦「復古氣質妝」，要不要先看看？

- **每答一題，妝容卡片就重排**：排序 = 膚色契合 + 臉型加分 + 妝容類型加分 + 情境加分（四項分開記）。
  實測：答「有精神」後復古氣質妝升到第一，再答「聚會晚宴」韓系微光妝升到第二。
- **中途點別的（例如「臉型是怎麼看的？」）不會把題目弄丟**：還沒回答的那一題，答案按鈕一直排在最前面。
- **商品頁的情境按鈕面板拿掉了**，只剩 AI 問、使用者答這一種方式。答過的題目商品頁不會再問，只問濃度；
  如果沒答完就先去看商品，商品頁會接著問剩下的。答案一樣會套用到商品（實測乾冷＋約會 → 唇彩換成水光的 #455）。

## 第一次想試化妝的人：把路鋪慢一點；說法改成建議句

### 先問一句「平常有在化妝嗎」

排在推薦畫面提問佇列的第二題（想看哪一類妝容 → **化妝經驗** → 心情 → 天氣 → 行程）。
問「平常有在化妝嗎」而不是「你是新手嗎」—— 前者是事實，後者像在評價人。

回答「🌱 第一次試試看」之後：

| 變的東西 | 做法 |
|---|---|
| 推薦順序 | 清淡好上手的加分、最濃的扣分（依妝容自己的濃度設定判斷：≤0.55 加 14、≥0.85 扣 16）。**扣分不是不給** —— 濃妝仍在清單裡，只是不放第一個。實測：復古氣質妝從第 2 名掉到第 4 名 |
| 濃度 | 整體再乘 0.85（實測 55 → 42）。太濃第一眼會嚇到，想更明顯隨時往右拉 |
| 每一步的提醒 | 第 2 步「先看唇色就好 —— 差別最明顯、也最好上手」／第 3 步「三件不用一次都用上，只換唇色別人通常就看得出來」／AR「先只動唇色；太明顯就把濃度往左拉」／回饋「第一次能找到一支喜歡的唇色就很夠了」 |

回答「偶爾」時方向一樣、幅度只有一半；回答「常化妝」則完全不動排序，也不給這些提醒（不囉嗦）。

### 說法從斷言改成建議

| 原本 | 現在 |
|---|---|
| 卡片標「最推薦」 | 「先從這款開始」 |
| 「推薦『自然偽素顏』：…」 | 「可以從『自然偽素顏』開始看看：…」 |
| 「綜合…最推薦『X』，要不要先看看？」 | 「綜合…我會先從『X』開始看看，你覺得呢？」 |
| 「這類顏色上臉會很乾淨」 | 「這類顏色通常會蠻乾淨的」 |
| 「顏色也跟你偏冷的膚色很搭」 | 「顏色跟你偏冷的膚色也蠻搭的」 |
| 「很襯鵝蛋臉」 | 「蠻襯鵝蛋臉的」 |

這一節只改「推薦」類的說法。**量測結果不跟著模糊化** —— 追問「臉型是怎麼看的？」時
仍然照實給 1.58 倍、96%、ΔE 這些數字；把有依據的數字也講得含糊，等於把誠實跟客氣搞混了。

`node test.mjs` 第 25 組（8 項）：三個答案都是已知動作、第一次的人清淡加分濃妝扣分、偶爾是一半、
常化妝不動、四個步驟各有一句提醒、以及掃過 35 條推薦文案不得出現「最適合／一定／必須／絕對／保證」。

依使用者給的流程整理，畫面的重點放在 **AI 對話** 與 **AR 體驗**：

| 顯示的步驟 | 內容 |
|---|---|
| 1 拍照 | 同前 |
| 2 AI 諮詢 | **先問、再建議**：天氣 → 心情 → 行程 → 妝容類型（AI 先判斷、請你確認）→ 化妝經驗。問的時候不顯示妝容卡片，問完才一次給臉型、膚色、小技巧與「我會先從哪一款開始看看」，卡片也在這時出現。不想回答可以點「⏭️ 直接看建議」 |
| 3 AR 試妝 | 建議之後**直接進 AR**，中間不再經過商品頁。調整時依剛才的回答給方向（見下表）。沒有鏡頭的機台改走「照片試妝」 |
| 4 商品推薦 | AI 在對話裡推薦**今天試過的那組**，可以直接「放進購物袋」；頁面順序改成 對話 → 推薦商品 → 試妝結果 → 評分 |

**AR 調整時的方向**（`adjustHint`、`shadeHint`，一律是建議句）：

| 情況 | AI 說 |

| 行程是上班／面試，濃度 > 70 | 「上班的話，可以稍微往左一點，比較不會太搶眼」 |
| 晚上約會／聚會，濃度 < 40 | 「晚上有約的話，可以再往右一點，燈光下會比較看得出來」 |

| 其他 | 依濃度分四段：很淡／日常剛好／有妝感／很濃 |

## 一步一步帶你畫：AI 引導 × AR × 學習

### 為什麼要有這個模式

原本的 AR 是「整組妝直接上好，你再慢慢調」。對第一次化妝的人，這等於跳過了學習 ——
看得到結果，卻不知道為什麼、也不知道回家怎麼畫。

引導模式改成**一層一層加上去**：先看素顏 → 眼影 → 腮紅 → 唇。每一步都做三件事：

1. **在鏡子上圈出要畫的地方**（AR 真正的用處：指的是「你的臉」，不是示意圖）
2. **一句怎麼做、一句常見的失誤**（學習）
3. **那一層才出現在鏡子裡**（看得到每一層的差別）

每一步都可以「這一步我自己畫」（直接進自己上妝、筆刷已切到該部位）或「跳過這一步」，隨時能結束；
中途結束會把整組妝補回去，不會留一張只畫一半的臉。走完之後回顧「今天跟著畫了哪幾個部位」，
並提醒在家也是同樣的順序。

- **新手一進鏡子就會被問**「要我一步一步帶你畫一次嗎？」—— 這是最需要、卻最不會自己按的功能。
- 步驟數寫在句子裡（步驟 2／3），永遠知道還剩幾步。
- 沒有的品項不排空步驟（男士妝沒有眼影、濃度是 0 的部位都會跳過）。

### 對話選項不再一次給十個

AR 的選項一度有十個，選項一多就難挑，引導的效果反而變差。現在**一次最多五個，其餘收在「⋯ 更多…」裡**；
進入引導模式時只留引導的四個選項（下一步／自己畫／跳過／結束），不讓人分心。

### 驗收

`test.mjs` 第 32 組 16 項（步驟順序與內容、沒有的品項不排、每步講第幾步與用哪一支、最後一步的按鈕、回顧只算真的做過的、三種語言文案）。
瀏覽器（假鏡頭）：新手進 AR 時 AI 主動問；走完 3 步、中間跳過一步 → 回顧只算做過的兩個部位；引導中濃度從 0 一層一層加上去；「這一步我自己畫」進手動上妝且筆刷已切到該部位，按完成回到引導的選項；選項列收成 5 個＋「⋯ 更多…」。

### 限制

- 引導只涵蓋這台機器畫得出來的部位（眼影、腮紅、唇）；底妝、眉毛只用說的。
- 「自己畫這一步」不會檢查你畫得對不對 —— 它不知道你有沒有畫在圈出來的位置。
- 步驟裡的做法是網路上美妝媒體與品牌的一般說法（同 `js/learn.js` 的來源），不是皮膚科或化妝品學的來源。

## 流行妝容：一份有日期、可更新的資料包

### 為什麼不是即時抓流行

機台是離線的（櫃位網路不穩、也不想把客人的臉送上網），所以**流行不是即時抓的，是人整理好寫進資料包的**。
因此每一筆都帶著**出處**與**整理日期**，對話裡會照實說「流行資料 2026-09 整理；機台離線，不會自己更新」，
設定面板也看得到版本與筆數。超過約半年沒更新，程式自己標成「有點舊了，聽聽就好」——
這比假裝自己很懂現在誠實得多。

每一筆都要**在這台機器上真的做得到**（對應到店裡有貨的商品、濃度，或是進自己上妝模式照著畫）；做不到的不放進來 —— 講了卻不能試，只是廣告。

| 曬感腮紅 | 頰 | 自己上妝：兩頰高處＋橫過鼻樑 |
| 莓果深色調 | 唇頰 | 深莓果唇＋同方向的淡腮紅 |

指定質地的流行（要光澤、要霧感）**先只從那個質地裡挑** —— 質地就是那個流行本身，不是加分項。

### AI 怎麼用它

- **推薦畫面**：季節正好襯某個流行時，順帶提一句（只提一次，不改推薦排序 —— 流行是參考，不是應該）。
- **「🗞️ 最近流行什麼？」**（推薦畫面與 AR 都有）：講名稱、為什麼在流行、兩句怎麼做、店裡最接近的是哪一支，最後附出處與資料日期。
- **「幫我套用這個」**：能換的就換（唇、眼、頰、濃度）；要自己畫的（高位腮紅、C 字腮紅、曬感腮紅）就直接打開自己上妝模式、切到腮紅。
- **排序**：襯這一季的排前面，再來看今天學到的喜好（喜歡暖色與喜歡冷色的人，推到的流行不一樣）；講過的不再講第二次；男士妝容只推適合的那幾個。

### 驗收

`test.mjs` 第 31 組 19 項（資料包有日期、每筆有出處、每個流行都對應得到有貨的商品或畫得出來、質地挑對、季節與喜好影響排序、講過不重複、過期判定、三種語言文案）。
瀏覽器（假鏡頭）：推薦畫面出現「你的冬季型正好很襯最近流行的『霧紫豆沙唇』」；點「最近流行什麼」講出完整四句與出處。

### 限制

- **流行資料要由人更新**：改 `js/trends.js` 的 `TREND_PACK` 日期與 `TRENDS` 內容即可，其餘（挑商品、排序、三語文案的鍵）都是照規則自動的。
- 來源是 2026 年的英文／日文美妝媒體，**偏歐美與日本**；台灣、韓國的流行不一定一樣。
- 「什麼在流行」本來就是編輯與媒體的說法，不是量出來的事實；所以句子都寫成「最近在流行」而不是「你應該」。
- 從推薦畫面直接套用流行時，若還沒選妝容，會先用推薦第一名當底再套 —— 這一段修好之後只跑過單元測試，
  瀏覽器驗收時 App 視窗被縮到背景（畫面與臉部追蹤會暫停），沒能再走一次。

## 唇色知識與喜好學習

### 把一支唇膏講成人話

色系由**實測色值**分（彩度 → 色相 → 明度），不是人工標的：

| 色號 | 色相 / 彩度 / 明度 | 色系 | 深淺 |
|---|---|---|---|
| #307 冷調正紅 | 24° / 65 / 43 | 正紅 | 偏深 |
| #620 莓果紫紅 | 6° / 48 / 41 | 莓果紫紅 | 偏深 |
| #118 玫瑰豆沙 | 24° / 37 / 55 | 玫瑰豆沙 | 中等 |
| #204 蜜楓棕 | 40° / 48 / 48 | 磚紅・楓葉棕 | 偏深 |
| #512 蜜桃汽水 | 38° / 43 / 64 | 珊瑚 | 偏淺 |
| #455 裸感奶茶 | 40° / 26 / 62 | 裸色 | 偏淺 |

換色號時，AI 會說「#512 蜜桃汽水屬於『珊瑚』色系，水光質地，顏色偏淺」，再加一句這個色系的特徵與適合的場合。
門檻是照這批商品與常見分類對出來的，換一批商品要重看一次。

### 學今天這個人喜歡什麼顏色

以前只記「停留過的底調」，現在記四個方向：**冷暖、深淺、鮮豔、質地**。

- 依據：**停留時間**（每 2.5 秒算 1 分，最多 3 分）與**自己點選**（再加 1.5 分）；只掃過去的不算。
- 看過的色號少於 2 支不下結論，照實說「還在看」。
- 只講明顯的方向（|值| ≥ 0.25）；四平八穩就說「接受度蠻廣的」，不硬選一邊。
- **講得出來**：AR 對話多了「💭 我的喜好學到什麼？」，結束畫面也會講今天的方向並挑一支最貼近的。
- **用得到**：「換下一個色號」學到喜好之後就照喜好挑（挑色時冷暖的權重是深淺、鮮豔的 1.6 倍 —— 冷暖是最看得出來的差別）；缺貨的永遠不推薦。

### 美妝知識（來自網路上的一般說法）

小教室多了 6 課唇色相關：**質地怎麼選**（霧面色準持久但放大唇紋／水光飽滿疊加更顯色但易掉／透明感最好上手）、
**MLBB**（My Lips But Better，比原本唇色好看一點點，最不容易出錯）、**唇色的影響**（唇膏疊在有血色的唇上，唇色深會更暗，想接近管子裡的顏色要先用遮瑕壓一下）、
**疊擦**（只塗中央往外抿＝自然；塗滿＋邊界清楚＝正式）、**唇部保養**（脫皮用溫熱毛巾、護唇膏等一兩分鐘再上色）、**試色的位置**（手背跟嘴唇顏色差很多，要看整張臉的氣色）。
小測驗也多了三題（MLBB 是什麼、唇色深擦淡裸色會怎樣、霧面最該注意什麼）。

參考：[Bobbi Brown 台灣](https://www.bobbibrown.com.tw/makeup-guide/lipsticks-choosing-tips)、[YSL 台灣](https://www.yslbeauty.com.tw/seo-makeup-3.html)、[Visée（コーセー）](https://www.kose.co.jp/visee/lip/type/)、[ちふれ](https://www.chifure.co.jp/kirei/useful/season/13)。

### 驗收

`test.mjs` 第 30 組 26 項（色系與色號名稱對得上、深淺、三種語言文案、喜好學習的門檻與方向、自己挑的權重較高、照喜好挑下一支、缺貨不推薦、唇的課與測驗）。
瀏覽器（假鏡頭）：換色號時講出色系與質地並給場合建議；「我的喜好學到什麼？」說出偏暖、偏鮮豔、常停在霧面並挑出 #204；結束畫面同樣講一次；英文、日文沒有漏翻。

### 限制

- 喜好是**這一次體驗**學到的，下一位客人重來（機台不留個人資料）。
- 停留時間只是「可能喜歡」的間接證據：有人是在猶豫、有人是在看手機；所以門檻設得保守，而且一定講出依據讓人可以否認。
- 色系門檻依這批商品調的；顏色落在邊界（例如豆沙與玫瑰之間）時，分到哪一邊會有點隨機。

## 自己上妝（手動上妝）加回來

AR 改成「鏡子為主＋底部抽屜」之後，手動上妝藏在抽屜「妝容調整」的第四個分頁，而且抽屜打開時會蓋住大半個鏡子 —— 選了也沒有臉可以畫，等於功能不見了。

- **三個入口**：鏡面左側「✍️ 自己畫」按鈕、AI 選項「我想自己畫畫看」、原本的「手動上妝」分頁。
- **進入後抽屜整個收起來**，整面鏡子都能畫；工具縮成底部一條：塗在哪裡（唇／眼／頰，附目前顏色）、該部位的色號、筆刷粗細、擦掉重來、完成。撤銷／重做沿用鏡面左上那一組。
- 進來時工具列上有一句怎麼畫（依部位：唇沿著嘴唇、眼從眼頭到眼尾、頰從蘋果肌往太陽穴），畫了第一筆就收起來。
- 按「完成」回到 AI 對話：有畫就肯定一下並提醒可以撤銷；沒畫就說下次怎麼進來。筆刷濃度與筆壓靈敏度仍在「妝容調整」裡。
- 驗收（手機尺寸）：進入後抽屜隱藏、工具列在底部 131px 內、臉的區域不被遮住；三個入口都能進、完成能回到對話。
  實際下筆需要臉部追蹤在跑，這次驗收時視窗在背景、追蹤暫停，沒有實測下筆（筆觸本身的程式沒有改動）。

## 季節判斷（春夏秋冬）＋美妝小教室＋AI 引導

### 季節怎麼判斷

四季是三個方向的組合：**冷暖 × 明度 × 清濁**。

| 季節 | 冷暖 | 明度 | 清濁 | 代表色 | 比較要小心 |
|---|---|---|---|---|---|
| 春 | 暖 | 亮 | 鮮豔清透 | 珊瑚、蜜桃、亮黃、嫩綠 | 太暗、灰濁 |
| 夏 | 冷 | 亮 | 柔和霧感 | 玫瑰粉、薰衣草、灰藍、灰米 | 太鮮豔、偏黃 |
| 秋 | 暖 | 深 | 沉穩霧感 | 陶土、芥末黃、卡其、酒紅 | 偏藍、粉嫩 |
| 冬 | 冷 | 深或對比強 | 鮮豔 | 正紅、桃紅、寶藍、純白 | 偏黃、灰濁 |

照色彩顧問的做法**分兩步**，不直接從四個挑一個：
1. 先分冷暖（沿用原本的底調殘差）→ 暖的是春或秋、冷的是夏或冬
2. 同一邊再分：**春 vs 秋 看明度**（膚色為主，加上頭髮與瞳孔有多深）；**夏 vs 冬 看清濁**（五官跟膚色的對比、黑白分明的程度）

從照片新量的：**瞳孔**（MediaPipe 478 點裡的虹膜點，取中段明度，避開瞳孔與反光）、**頭髮**（找到髮際線時，往上一小段的中位數明度；找不到就不量、照實說）。

分不開時照實說「介於兩季之間」，並**只在這時候**多問一題自我檢查（常用的三個方法）：
冷暖不確定 → 「金色和銀色飾品，哪個讓臉比較亮？」；春秋分不開 → 「明亮的珊瑚色還是沉穩的磚紅色比較襯？」；夏冬分不開 → 「穿黑色上衣，臉看起來俐落還是沉重？」。回答會蓋過照片的估計（權重 0.65）。

### 季節怎麼影響推薦

- **商品屬於哪一季用實測色值算**，不靠人工標：冷暖取商品的底調標記，明度與彩度取 Lab；春秋主要看明度、夏冬主要看清濁 —— 跟判斷人的方式一致。
  結果：蜜桃汽水→春、蜜楓棕→秋、冷調正紅／莓果紫紅→冬、玫瑰豆沙／裸感奶茶→夏。
- **挑色號**：有季節時，季節契合度為主（以 0.5 為中點放大，差 0.2 就蓋得過質地偏好）、底調為輔。同一個自然妝：春→蜜桃汽水、秋→蜜楓棕、夏→裸感奶茶、冬→冷調正紅。沒有季節時行為完全不變。
- **AR 換色號**：很搭就說一聲；偏離比較多就說它比較像哪一季，並給一支更搭的。中間地帶不講，免得每換一支都評論。

### 美妝小教室與小測驗

- 13 課，每課一件事、兩三句、用動作講：上妝順序、粉底薄擦、唇膏拍開、腮紅少量多次、眼影三步、眉毛、唇峰（進階）、持妝、季節色怎麼用、冷暖的誤會、冷暖自我檢查、試色的光線、男士保養。
- **配合當下挑課**：AR 裡正在調唇就教唇；有季節結果先教季節色；新手不教進階；男士先教男士保養；學過的不重複。
- 小測驗：優先出「這支唇色像哪一季」—— 用店裡真的有的色號，答案由色值算出來，只出分得很開的；再來是觀念題（皮膚白就是冷調嗎？春秋差在哪？…）。答錯不說「錯」，說「差一點」＋答案＋解說；一題都沒答對時結束回顧不報 0 分。
- 推薦畫面、AR、結束畫面都有「教我一個小技巧」；推薦與結束畫面有「考考我」。結束時回顧今天學了哪幾課、答對幾題。

### 驗收

`test.mjs` 第 29 組 35 項（四種典型人各判對、兩步判斷不跨軸、分不開時問對的那一題、回答會改結果、商品季節、挑色號、對話、小教室、小測驗、三種語言文案齊全）。
瀏覽器（假鏡頭，手機尺寸）：測試臉判為冬季型，推薦出現季節與四個色票、「季節是怎麼判斷的？」「我適合哪些顏色？」「教我一個小技巧」「考考我」都能用；AR 換到蜜桃汽水時提醒它偏春季、建議冷調正紅；結束畫面回顧學到的兩課；英文、日文沒有漏翻。

### 限制

- **門檻只用一張測試臉與合成數據看過**，沒有經過多人、多種膚色的校正；介於兩季之間的判斷也會受光線影響（光線不準時，前面的顏色校正提醒一樣會出現）。
- 照片量不到真正的「披布比對」；對話裡明說最準的方法是自然光下、素顏、拿不同顏色的布比對。
- 頭髮染色、瀏海、帽子會讓頭髮量不到或量到染後的顏色。
- 目前店內商品沒有秋季的腮紅（陶土色），秋季的人會拿到最接近的暖色腮紅。
- 參考：[メグラシ：春vs秋は明るさ、夏vs冬は濁り](https://lifestyle-media.air-closet.com/know/personal-color/four-seasons-comparison)、[Curate Your Style：What Is Seasonal Color Analysis?](https://www.curateyourstyle.london/blogs/colour-seasons)

## 色卡校正：參考 ZOZOGLASS 的做法

### 想解決的問題

膚色判定最怕的是**櫃位燈光**。之前唯一的參考是眼白：假設眼白是白的，看它被照成什麼顏色，就把整張照片「每個通道乘一個倍數」拉回來。
這有兩個先天限制：

1. 每個人的眼白本來就不是純白，而且常常被睫毛、反光擋住（假鏡頭這張臉就讀不到，只能不補償）；
2. 一個參考點只能修「整體偏黃／偏藍」，修不到鏡頭本身的色彩偏差（例如紅色拍成偏橘、綠色串到紅色）。

### ZOZOGLASS 怎麼做

[ZOZOGLASS](https://zozo.jp/zozoglass/) 是 ZOZO 的膚色量測眼鏡。官網的說明：戴上眼鏡、看著手機畫面把臉轉幾個角度，
從影像推估皮膚裡的**血紅素與黑色素量**來量膚色；**戴著它量就不受環境光影響**，所以線上也能量得準；
結果分黃調／藍調與春夏秋冬四型，並推薦最接近的底妝色號。
鏡框上有一圈特殊圖樣，拍照時跟臉一起入鏡當作參考（[使用心得](https://vitalify.jp/blog/2021/04/zozo-glass%E3%81%8C%E5%B1%8A%E3%81%84%E3%81%9F%E3%81%AE%E3%81%A7%E3%82%84%E3%81%A3%E3%81%A6%E3%81%BF%E3%81%9F%EF%BC%81.html)）。
ZOZO 沒有公開演算法細節；這裡借用的是它的**原理**，演算法是自己寫的（線性 RGB 的色彩校正矩陣，不是血紅素／黑色素推估）。
重點是「**已知顏色的參考物跟臉在同一張照片、同一個光線下**」。

### 機台版的做法

客人不會戴眼鏡，所以把參考物換成固定在鏡框邊的一張 **ColorChecker Classic 24 色卡**（鏡頭拍得到、不擋臉）：

| 步驟 | 做什麼 |
|---|---|
| 設定一次 | 店員開 `_chart.html`，在畫面上點色卡色塊區的四個角（**順序不拘**，畫面鏡像或色卡轉 90° 都沒關係 —— 程式試 8 種擺法，留校正後色差最小的） |
| 每次拍照 | 讀 24 塊的顏色 → 在線性 RGB 上用加權最小平方擬合 **3×3 色彩校正矩陣**（兩塊膚色色塊權重 3、中性灰 2）→ 校正膚色再判定 |
| AR 每一秒 | 重讀色卡、重新擬合，渲染器用同一個矩陣把畫面換成「標準光下的顏色」再上妝 —— 櫃位換燈也跟得上 |
| 讀不到時 | 過曝／太暗的色塊不採用；可用的少於 8 塊、或校正後色卡仍差 ΔE > 6（被擋住、移位、反光）→ 不採用，退回原本的眼白 → 高光 → 不補償 |
| 上傳照片 | 不讀色卡（照片裡沒有機台的色卡，避免照片內容剛好被當成色卡） |

有色卡時，「光線有影響嗎？」的回答會改說：讀到幾塊、校正前後色卡偏了多少。畫面底部狀態列會多一個「色卡校正」。

### 結果

**模擬**（`test.mjs` 第 27 組；燈光色偏 × 鏡頭通道串色 × 曝光 0.85 × 雜訊）：

| 燈光 | 不校正 ΔE | 只用白色（等同眼白）| 色卡矩陣 |
|---|---|---|---|
| 鹵素 2700K | 18.0 | 9.3 | **0.8** |
| 暖白 LED 3500K | 13.3 | 8.3 | **0.7** |
| 冷白 6500K | 10.3 | 7.2 | **0.7** |
| 日光燈偏綠 | 12.0 | 7.8 | **0.7** |

膚色（6 種膚色 × 4 種燈光）：色卡矩陣平均 ΔE **0.7**、色相誤差 1.3°；只用白色 ΔE 4.4、2.2°。
鏡像畫面＋亂序點四角：自動找到正確擺法（ΔE 0.9），照「螢幕左上」當第一塊的錯誤擺法色差大很多。

### 放進主程式：設定面板 ＋ 需要時由 AI 引導

每次拍照分析完，會判斷「這次的顏色量得準不準」（`colorStatus`，`js/advisor.js`）：

| 狀況 | 等級 | 主程式怎麼做 |
|---|---|---|
| 讀到色卡 | 準 | 不打擾 |
| 沒有色卡、眼白讀得到、一般白光（4000–7500K）| 準 | 不打擾 |
| 眼白讀得到，但光線明顯偏暖（< 4000K）或偏冷（> 7500K）| 建議 | AI 說「已經修正過，想更準可以用色卡」 |
| 眼白讀不到或不可信（也沒有色卡）| 需要 | AI 提醒「冷暖可能有點偏，參考看看就好」 |
| 設定過色卡，這次卻讀不到 | 需要 | AI 提醒色卡可能被擋住或移動了 |

- **AI 引導**（推薦畫面，講完膚色之後）：只有「建議」「需要」時才講，並多一個選項「怎麼讓顏色更準？」→
  先說為什麼可能偏，再給兩條路：**換到白光、光線平均的地方重拍**（誰都做得到），或**用色卡校正** →
  選項「打開顏色校正設定」「換個光線重拍」「先這樣就好」。語氣是建議，不說「結果是錯的」。
- **設定面板**（右上角 ⚙ → 顏色校正）：這次量得準不準、色卡是否設定、螢幕是否校色；按鈕「設定色卡」「清除色卡」「螢幕校色」。
  設定頁開在**新分頁** —— 直接換頁的話照片、對話、購物袋都會不見。可能量不準時，齒輪上亮一個小點。
- **設定完回來**：切回主程式分頁時會偵測到色卡設定好了，AI 說「重拍一次就會用色卡校正」並給「換個光線重拍」。
- 假鏡頭測試頁 `_camtest.html?chart=warm` 的「設定色卡」會開 `_chart.html?sim=warm`，整條流程在沒有實體色卡時也能走一遍。

驗收（瀏覽器，手機尺寸）：沒色卡 → 出現提醒、齒輪亮點、引導三句與三個選項、設定面板打開並顯示「✕ 找不到可以參考的白色」；
色卡位置錯 → 「色卡這次好像讀不到」；色卡正確 → 「✓ 這次用色卡校正（ΔE 0.4）」、提醒與亮點都消失。`test.mjs` 第 28 組 12 項。

### 限制（要老實說）

- **需要實體色卡**：ColorChecker Classic 24 色（或同規格）。沒有色卡時一切照舊走眼白。
- **參考值是公開的 sRGB 近似值**：每一批色卡、以及色卡褪色後會有差異；要更準應該用分光儀量自己那張，換掉 `js/chart.js` 的 `CHART24`。
- **模擬 ≠ 真機**：真實鏡頭有非線性的色調曲線、自動白平衡／自動曝光會一直變、邊角暗角；3×3 矩陣修不到非線性的部分，真機效果會比模擬差，需要在店裡實測。建議把相機的自動白平衡鎖住。
- **色卡要跟臉在同一個光線下**：色卡被陰影遮到、或正好反射燈光，校正會偏；程式能擋掉「偏很多」的情況（ΔE > 6），擋不掉「偏一點」。
- **位置存在瀏覽器裡**（localStorage，每台裝置、每個網址各一份）：換機器、清瀏覽資料、或開單檔版（file://）都要重新設定一次；鏡頭或色卡移動過也要重設。
- **只校正「判定」與 AR 的光線模型**，不處理螢幕顯示的偏差 —— 那是 `_calib.html`（色差儀）的工作，兩者互補。

## 主軸二：AR 體驗與還原度（這一輪新增）

顏色還原的部分見〈AR 顏色還原〉與〈補做〉。這一輪再加三件直接服務「體驗 × 還原度」的東西：

### 唇部放大檢視

色號之間在唇上的差別本來就不大（量測台實測：有貨色號彼此最多 ΔE 7），在一個小鏡面裡更難判斷。
鏡面左上多一顆「放大唇部」，開啟後在鏡面右側疊一塊放大的唇部。

**只是放大同樣的像素，不動顏色** —— 放大鏡如果順手「加強一下」，就變成另一種失真。
對話裡也是這樣講的。

### 現場光線的誠實提示

還原度取決於光線：眼白量得到時最準；退到臉上的高光會差一點；太暗時連相機本身都在猜。
AR 每秒重估一次，狀態改變時主動說：

- 畫面平均亮度低於 18% →「現場光線偏暗，螢幕上的顏色會比實品暗，建議換個亮一點的位置」
- 眼白量不到、改用高光 →「顏色的準度會比平常低一點」
- 兩者都估不出來 →「直接沿用相機的白平衡，與實品可能有落差」

`node test.mjs` 第 15 組驗這段的判斷順序（太暗優先、估得到就不囉嗦、一律標成「留意」）。
